# 格物 Lattice：代表性 GitHub AI 项目系统分析与架构优化方案

> 版本：2026-09-29  
> 分析对象：GitHub 上具有代表性的 AI 应用、RAG、Agent、MCP 与知识库项目  
> 本项目基线：当前工作区（包含未提交的 AI 相关增量实现）  
> 目标：在不破坏“Markdown 文件为真源、SQLite 仅作可重建投影、本地优先”的前提下，完善功能、提升检索与执行质量，并建立可量化的性能、可靠性和用户体验门禁。

## 0. 结论先行

Lattice 不需要复制 Dify、Open WebUI 或 AFFiNE 的全部系统。它最有价值的路线是：

1. 保留当前的模块化单体、文件真源和 SQLite 投影；不为单机单用户场景提前拆成微服务。
2. 把现有 AI 能力从“可用功能”提升为“可验证产品”：检索可调试、引用可追溯、工具操作可审计、索引可恢复、模型失败可解释。
3. 先补齐附件、模板、每日笔记、大纲、版本历史和导出等笔记应用基本盘，再把语义搜索、相关笔记和自动双链作为差异化主线。
4. 将同步、索引、Embedding、摘要和导出统一为后台任务，前台请求只负责创建任务、读取状态或消费 SSE 事件。
5. 将“行业领先”定义为可复现的指标：核心操作延迟、检索 Recall@K、引用有效率、写入零丢失、任务恢复成功率和用户任务完成率，而不是功能数量。

当前工作区的 `npm run verify` 已通过：服务端 91 项测试、前端集成/冒烟 62 项检查、MCP stdio E2E 均通过。该结果证明现有增量具备可继续演进的基础，但不等同于大规模性能、真实模型质量或多设备冲突已经达标。

## 1. 分析范围与方法

### 1.1 项目选择

项目分为两组：

| 组别 | 项目 | 主要观察点 |
| --- | --- | --- |
| AI 应用与 RAG | [Open WebUI](https://github.com/open-webui/open-webui)、[Dify](https://github.com/langgenius/dify)、[AnythingLLM](https://github.com/Mintplex-Labs/anything-llm)、[Khoj](https://github.com/khoj-ai/khoj)、[FastGPT](https://github.com/labring/FastGPT)、[LobeHub](https://github.com/lobehub/lobehub) | Provider 抽象、RAG、Agent、工具调用、异步任务、可观测性、交互形态 |
| 知识库底座 | [AFFiNE](https://github.com/toeverything/AFFiNE)、[SiYuan](https://github.com/siyuan-note/siyuan) | 本地优先、文档/块模型、协作、索引、备份和数据可迁移性 |

选择标准是：GitHub 活跃度、功能代表性、源码可读性、与本地知识库场景的相关性。GitHub Star 只作项目影响力的时间点参考，不作为质量的唯一判断。研究数据通过 GitHub 公共 API、项目 README、源码目录和依赖清单核对，抓取时间为 2026-09-29。

### 1.2 评价维度

- 核心功能：用户最常用的闭环是否完整，失败时是否有可恢复路径。
- 技术架构：模块边界、进程边界、数据真源、任务执行和扩展点。
- 算法与模型：Embedding、分块、召回、重排、工具循环和模型适配策略。
- 性能优化：启动、索引、检索、流式输出、前端渲染和资源占用。
- 用户体验：首次配置、可解释性、引用、确认、进度、错误和隐私提示。
- 可迁移性：是否值得把“思想”带回 Lattice，还是会引入不必要的复杂度。

### 2.2 Open WebUI：Provider、流式和知识库入口

**核心功能**：围绕聊天建立模型、知识库、工具、Agent、Notes、文件和多模型协作；支持 Ollama 与 OpenAI-compatible API，并通过 `#` 等交互把知识库/文件快速带入会话。

**架构设计**：前端与 Python 后端分层，模型服务、数据库、文件存储和向量库均有适配层。README 明确列出 SQLite/PostgreSQL、多个向量数据库、BM25 + 向量检索、重排和全上下文模式。它把“模型连接”与“模型能力”分开：同一个基础模型可以配置系统指令、工具和知识。

**算法与模型**：不绑定单一 LLM；Embedding、BM25、向量库和 reranker 均可替换。优点是覆盖面大，代价是适配矩阵、部署复杂度和质量差异都上升。

**性能与 UX**：流式输出、多模型并行、PWA、模型/知识库入口靠近聊天输入区，降低功能发现成本；离线运行和 Provider 无关性也降低了首次使用的隐私阻力。

**对 Lattice 的借鉴**：

- 保留 OpenAI-compatible 作为最小兼容协议，不把某一家厂商的 SDK 当领域模型。
- AI 面板要展示检索来源、模型状态和隐私边界，不能只显示一个“正在思考”。
- 多 Provider 是配置能力，不代表要马上接入多个向量数据库；Lattice 的单机规模首先适合 SQLite。

### 2.3 Dify：把 AI 能力做成可观测的任务系统

**核心功能**：可视化工作流、RAG Pipeline、Agent、模型管理、工具/MCP、应用发布和生产观测。它的优势不是某个模型，而是把 Prompt、检索、工具和输出连接成可以测试、运行和追踪的流程。

**架构设计**：源码依赖清单体现出 Flask API、Celery、Redis、PostgreSQL、SSE/WebSocket、对象存储、插件和多种向量库。耗时的解析、Embedding、工作流执行和追踪不应阻塞 API 进程，这是 Dify 的核心工程经验。

**算法与模型**：模型供应商、向量库、Trace 后端都通过 Provider/Plugin 机制扩展；RAG 不只是“把前几段文本塞给模型”，还需要数据清洗、分块、召回、重排、上下文组装和评测。

**性能与 UX**：画布式工作流让复杂流程可见，运行记录和 Trace 让问题可定位；但部署组件很多，对桌面单机产品是明显的运营负担。

**对 Lattice 的借鉴**：

- 复制“任务状态 + 进度 + 可重试 + Trace”的方法，不复制 Celery/Redis/PostgreSQL 全套基础设施。
- 将 `reindex`、每日摘要、导出、批量 AI 操作设计为后台任务，返回 `jobId`，而不是把长操作绑在一个 HTTP 请求里。
- 引入最小的检索评测集和运行记录，解决“模型为什么没有用到我的笔记”的定位问题。

### 2.4 AnythingLLM：工作区和独立 Collector

**核心功能**：以 Workspace 组织知识库、对话和 Agent；支持本地/云模型、文件导入、RAG、工具和多种向量数据库。

**架构设计**：仓库明确分为 `frontend`、Node `server` 和独立 `collector`。server 处理会话、权限、模型与向量操作；collector 负责 PDF、Office、网页、OCR 等文档解析和切块。依赖清单包含 LangChain splitters、tiktoken、Transformers.js、LanceDB、Qdrant、Chroma 等，说明它把“文档处理复杂度”隔离成了单独边界。

**算法与模型**：支持远程 Embedding，也支持本地 Transformers.js；多向量库让部署可扩展，但也要求统一向量维度、模型版本和迁移策略。

**性能与 UX**：Workspace 是很好的信息架构：用户先选一个工作上下文，再决定模型和工具；文档处理异步化避免聊天被大文件导入拖住。

**对 Lattice 的借鉴**：

- Lattice 当前不需要新增进程，但应该在代码层先建立 `document-parser`、`embedding-job`、`retrieval` 的边界，以便未来迁移到 Worker Thread 或独立进程。
- 将“索引状态、失败原因、重试次数和最后成功时间”放到 UI；没有进度的索引在用户看来就是卡死。
- 不直接引入 LangChain：当前 Markdown 语法、双链和标题锚点是 Lattice 的优势，通用解析器反而可能破坏语义。

### 2.5 Khoj：个人第二大脑的高频入口

**核心功能**：从本地/在线资料中搜索和问答，创建带人格、知识和工具的 Agent，并执行定时自动化任务。

**架构设计**：依赖清单体现出 FastAPI/Django、PostgreSQL/pgvector、sentence-transformers、Transformers、调度器和 MCP。它把语义索引、Agent、定时任务和个人知识库连成一个闭环。

**算法与模型**：同时支持本地 Embedding、云端 LLM、文档分块和向量检索。其产品价值不是“更大的模型”，而是让搜索、问答、Agent 和自动化共用同一份个人上下文。

**性能与 UX**：自动化和 Agent 适合后台运行；用户需要知道任务何时执行、用过哪些来源、输出保存到哪里。个人知识库场景不应强制用户维护复杂的工作流图。

**对 Lattice 的借鉴**：当前 `AI_DIGEST_HOUR` 和 Journal 摘要是正确方向，但应继续补充任务历史、失败重试、来源引用和“停止自动化”入口。

### 2.6 FastGPT：RAG 质量工程和可视化 Flow

**核心功能**：知识库数据处理、模型调用、RAG 检索、Agent Skill、MCP 和 Flow 可视化编排。

**架构设计**：pnpm/Turbo monorepo 将 app、service、web、admin、SDK 和测试拆开；其测试脚本明确区分 workspace、vector 和 integration。它的工程价值在于把数据处理、运行时和验证分开，而不是把所有逻辑堆进聊天接口。

**算法与模型**：重点在切块、召回、重排、引用和可调试性；工作流层允许将检索、模型、条件和工具组合起来。

**性能与 UX**：可视化流程降低复杂能力的学习成本，检索测试和知识库管理增强可解释性；但 Flow 引擎会带来状态持久化、版本、执行沙箱和调试成本。

**对 Lattice 的借鉴**：优先做轻量的“检索调试视图”和固定任务模板，不做通用 Flow 编辑器。Lattice 需要的是可理解的个人工作流，而非低代码平台。

### 2.7 LobeHub：Agent 作为工作单元

**核心功能**：Agent Builder、Agent Group、Skills、MCP、Schedule、Workspace、Pages 和白盒记忆，强调 Agent 长期工作和多 Agent 协作。

**架构设计**：仓库采用 TypeScript monorepo，包含 packages、business packages、Next.js、Vite SPA、桌面端和 Drizzle 数据层。模块化和多端复用做得很强，但它的组织成本远高于单机知识库。

**算法与模型**：核心不是单一检索算法，而是 Agent/Skill/工具协议、上下文和记忆的组合。模型可替换，能力由工具边界决定。

**性能与 UX**：把 Agent 从一次性对话提升为“可配置工作单元”，配合 Schedule 和 Workspace；白盒记忆让用户可以检查和修改系统记住的内容。

**对 Lattice 的借鉴**：把“会话、知识库、操作计划、任务历史”作为一组可追踪资源；但不引入多 Agent 协作，当前单用户的关键是可信、可回滚和不打扰。

### 2.8 AFFiNE 与 SiYuan：底座取舍的参照

**AFFiNE** 采用本地优先、实时协作和 CRDT/块引擎，适合多人协作和复杂工作区，但也意味着同步、冲突、存储格式和运行时复杂度同时上升。

**SiYuan** 采用 Go 内核、SQLite 和块级知识模型，提供块引用、CLI 和 Agent/MCP 生态。它证明块级引用能力很强，也反向说明数据库真源带来备份、升级和迁移成本；其文档明确提醒不能只备份活动 SQLite 索引，且同一工作区要遵守单写者约束。

**对 Lattice 的结论**：继续使用 Markdown 文件作为真源。用标题锚点、可选块 ID、稳定文件路径和版本侧车满足大多数引用需求，暂不迁移为块级数据库，也不引入 CRDT。

## 3. Lattice 当前架构画像

### 3.1 已有技术栈与边界

| 层 | 当前实现 | 判断 |
| --- | --- | --- |
| 桌面壳 | Electron，负责窗口、后端进程、Vault 配置和安全导航 | 适合本地优先；需继续加固 URL、IPC 和崩溃恢复 |
| 前端 | React 18 + Vite 5，无大型状态库和路由依赖 | 轻量；需治理请求竞态、长列表、编辑器重渲染 |
| API | Express 5 + Zod 边界校验 + 结构化错误/请求 ID | 边界清晰；需统一长任务与版本并发契约 |
| 真源 | Vault 内 Markdown / Canvas 文件 | 应保持不变，任何索引都可删除重建 |
| 投影 | Node `node:sqlite`，迁移版本化，FTS5 trigram，标签/链接/文件路径投影 | 适合个人库；需持续验证 Node SQLite 稳定性和同步 I/O 影响 |
| Vault 同步 | `watcher` → `sync` → 增量投影，支持外部文件变化 | 方向正确；仍需冲突识别、任务化和重试状态 |
| AI Provider | OpenAI-compatible，支持多聊天 Provider、Embedding、连接测试 | 选型合理；需模型版本、限流、重试和密钥存储策略 |
| AI 检索 | FTS5/trigram + Embedding 余弦 + RRF，按标题分块，支持引用校验 | 已具备产品骨架；需评测集、重排门槛和索引观测 |
| AI 执行 | assist/agent 模式、读自动执行、写操作预览/确认/审计、轮次上限 | 安全边界优于“直接让模型改文件”；需防提示注入和并发写入 |
| 外部 Agent | MCP stdio，暴露 list/search/read/create/update | 生态接口已形成；需权限、配置导出和版本契约 |

### 3.2 当前已实现能力

源码和测试显示，工作区已包含以下能力：

- `/api/ai/chat` 与 `/api/ai/chat/stream`，SSE 事件支持流式对话。
- 多 Provider 与 Embedding 配置、连接测试、服务端设置持久化。
- `ai_sessions` / 消息持久化、重命名和删除。
- `note_chunks`、Embedding BLOB、模型过滤、向量余弦、块级向量复用和增量索引状态。
- FTS + 语义双路召回、RRF 融合、短笔记全文逃生门、引用编号校验和检索预览。
- 相关笔记/双链建议、受控标签建议、编辑器写作辅助和每日摘要。
- Agent 工具循环、文件读写动作预览/确认/审计，viewer 角色禁止自动写入。
- MCP stdio Server 及 `list_notes`、`search_notes`、`read_note`、`create_note`、`update_note`。

这些能力已经足够进入“质量和可靠性优化阶段”，不应再以“先做一个 AI 助手”为名重复建设聊天面板。

### 3.3 主要缺口与风险

| 优先级 | 缺口 | 影响 |
| --- | --- | --- |
| P0 | 当前 AI 新增模块、MCP 脚本和迁移仍有未跟踪文件；需先纳入版本控制和 CI | 发布包可能缺文件，回滚和协作不可审计 |
| P0 | 文件、SQLite 投影和 AI 索引之间缺少统一的任务状态/一致性视图 | 外部修改、断电、模型失败时难以恢复 |
| P0 | AI Key 仍需统一到桌面端安全存储或服务端密钥存储 | 明文出现在浏览器配置或备份中的风险 |
| P0 | Agent 读取的笔记内容是不可信输入，提示注入和越权路径需要专项测试 | 可能诱导模型执行危险操作或泄露上下文 |
| P1 | 附件、模板、每日笔记、大纲、版本历史、导出未完成 | 笔记应用基本盘不完整，AI 功能价值受限 |
| P1 | 多设备冲突只靠外部同步工具，缺少显式冲突面板 | 可能静默覆盖或产生重复笔记 |
| P1 | 预览、保存和侧栏仍有固定延时、全量刷新、请求竞态 | 大文档和快速切换时出现卡顿或旧响应覆盖新内容 |
| P2 | 语义检索没有离线评测集和用户反馈闭环 | 无法知道召回是否真的优于 FTS |
| P2 | 线性向量扫描没有规模阈值与迁移开关 | 个人库扩大后可能拖慢查询和事件循环 |
| P2 | 没有统一 metrics/trace，模型成本、首 token、索引吞吐不可观测 | 不能做性能回归和 Provider 成本控制 |

## 4. 目标架构

### 4.1 设计原则

1. **文件真源优先**：任何 SQLite 表、向量、缓存、任务状态都可删除后从 Vault 重建。
2. **同步写入短、异步计算长**：保存文件和更新基础投影是用户路径；Embedding、摘要、导出、批处理走任务队列。
3. **模型是适配器，不是领域对象**：核心业务只依赖 `chat()`、`streamChat()`、`embed()`、`testConnection()` 四个能力。
4. **工具最小权限**：读操作可自动执行；写操作必须有计划哈希、权限校验、用户确认和审计记录。
5. **先测量再升级**：SQLite 线性向量搜索、Worker Thread、sqlite-vec、独立进程都必须有基准数据后再引入。
6. **所有 AI 结论有来源**：模型回答、建议链接、自动摘要都带来源或明确标注“未使用知识库”。

### 4.2 高层结构

```text
Electron Shell / Browser
        │ HTTP + SSE + MCP stdio
        ▼
```

## 5. 功能完善方案

### 5.1 P0：稳定性、安全和可恢复性

#### 5.1.1 版本控制和发布门禁

1. 将 AI 模块、迁移、MCP Server、测试和文档纳入 Git；清理 `.gitignore` 中误伤源码的规则。
2. 在 CI 中运行 `npm run verify`、构建、迁移空库和一次最小 MCP E2E。
3. 发布前检查：迁移文件完整、前端产物存在、MCP 依赖可安装、Electron 包含 server/web 运行时。
4. 每个数据库迁移附带向前迁移、重复运行、旧数据和失败回滚测试。

#### 5.1.2 文件与投影一致性

- 写入顺序统一为“临时文件 → 原子替换 → 更新 SQLite 投影”；文件写失败时不得提交新投影。
- `notes.file_path` 唯一，创建同名标题时通过稳定 ID 或安全文件名避免覆盖。
- 记录 `content_hash`、`projection_version`、`last_indexed_hash` 和 `last_embedding_model`。
- watcher 事件进入去重队列；未知目录事件触发可观测的 membership repair，而不是静默丢弃。
- 应用启动只在投影缺失、迁移版本不匹配或 repair 被请求时做全量扫描。

#### 5.1.3 安全边界

- AI 读取的 Markdown、frontmatter、Canvas 和外部文件全部视为不可信数据；模型输出不能改变系统权限。
- 写操作必须携带 `planHash`、操作类型、源/目标路径、用户角色和确认时间；执行前再次做 Vault 路径和 symlink 校验。
- 统一服务端保管 API Key；桌面端优先使用 Electron `safeStorage`，浏览器只显示掩码状态，不回显完整 Key。
- 限制模型请求体、单次读取文件数、Agent 轮数、单文件写入字节数和总任务时长；每一项超限返回可解释错误。
- 全局校验 Host/origin、外链协议、SVG 资产响应和 CSP；MCP 配置不允许把任意命令静默加入项目级启动。

### 5.2 P1：补齐笔记应用基本盘

#### A. 附件

- Vault 约定 `_attachments/`，支持设置自定义目录和按年月分层。
- `POST /api/attachments` 使用白名单 MIME、大小上限、随机存储名和 sha256；不接受用户提供的绝对路径。
- Markdown 使用 `![[image.png]]` 与现有嵌入管线统一解析；附件引用计数、孤儿扫描和删除预览可见。
- 验收：图片粘贴、重启、外部移动、白板引用、导出和不支持类型都可恢复或明确提示。

#### B. 模板、每日笔记和大纲

- `_templates/` 模板支持 `{{date}}`、`{{time}}`、`{{title}}`，创建操作走统一 notes service。
- 每日笔记是确定性路径规则，不创建重复文件；失败时打开已有文件。
- 大纲基于已有 Markdown heading token，纯前端渲染并支持编辑/预览同步跳转。

#### C. 版本历史

- 快照存 Vault 的 `.lattice/history/<noteId>/<timestamp>.md`，不进入 SQLite 真源投影。
- 保存成功且内容 hash 变化后按时间窗口快照；7 天内保留全量，之后按日保留。
- 提供 diff、预览和恢复；恢复前创建当前版本快照，确保可逆。

#### D. 属性视图和导出

- 解析 frontmatter 到 `notes.properties` JSON 投影，首版只支持字符串、数字、布尔、日期和列表。
- `.view.json` 保存视图定义；支持按目录、标签、属性过滤，表格/卡片布局和排序。
- 先做静态 HTML 站点导出；Pandoc/docx/PDF 作为可选外部能力，不把系统安装依赖写死在核心路径。

### 5.3 P1/P2：AI 原生知识工作流

#### A. 语义搜索和相关笔记

现有 Embedding 管线继续使用“配置即启用、未配置即本地关键词”的策略：

1. 分块以标题层级为边界，保留 `noteId`、`filePath`、`anchor`、`contentHash`、`model`、`dim` 和 `ordinal`。
2. 笔记保存后只入队变更块；相同 `contentHash + model + dim` 复用向量。
3. 查询使用 FTS5/trigram 和向量两路召回，先用 RRF；只有质量评测证明有收益时再加 reranker。
4. 相关笔记建议排除自己、已有链接和同标题文件，显示“语义相关/关键词命中”的原因。
5. 新增反馈按钮：相关/不相关/忽略；反馈写入匿名的本地评测数据，不上传笔记内容。

#### B. 引用知识库问答

- 默认 top 6 个上下文块，短笔记可整篇注入；大笔记显示标题锚点和摘要。
- 模型只能使用服务端生成的 `[n]` 编号；服务端将编号映射为真实 note id、path、anchor 和 excerpt。
- SSE 增加 `citation`、`tool`、`status` 事件，前端可以边输出边展示来源和工具状态。
- 检索调试视图展示 FTS 命中、语义命中、RRF 分数、最终上下文和失败原因；不把内部 Key 或完整隐私内容写入普通日志。

#### C. 自动双链和受控打标

- 保存完成后后台生成 top-k 建议，不自动写回文件。
- 用户点击接受后，在编辑器草稿层插入双链；并发版本变化时要求重新确认，不覆盖新内容。
- 标签建议只从已有标签词表中选择，降低模型生成脏标签的概率。

#### D. Agent、MCP 和每日摘要

- Assist 模式：读操作自动执行，写操作预览后确认。
- Agent 模式：轮次上限、工具白名单、viewer 强制只读；任何自动写入仍进入审计历史。
- MCP 默认只暴露当前 Vault，工具输出截断并标记来源；MCP update/create 需要与本地角色策略一致。
- 每日摘要使用任务记录、幂等键和失败重试；生成的 Journal 笔记必须列出当天使用的笔记来源。

## 6. 算法、模型和技术选型决策

### 6.1 模型选型矩阵

| 能力 | 首选 | 备选 | 选型依据 |
| --- | --- | --- | --- |
| 对话/写作 | OpenAI-compatible Provider | 本地 Ollama/LM Studio | 不绑定供应商；用户能按隐私、成本和质量切换 |
| Embedding | 用户配置的 OpenAI-compatible embedding | 本地 Transformers.js 小模型（后置） | 当前零原生依赖；云端质量好，本地模式保隐私但安装包和 CPU 成本高 |
| 关键词 | SQLite FTS5 trigram + LIKE 兜底 | 外部搜索引擎（不建议当前引入） | 中文子串、零服务依赖、可随投影重建 |
| 向量存储 | SQLite BLOB + Float32Array | sqlite-vec / 独立向量库 | 个人库简单可靠；只有基准超过阈值才升级 |
| 融合排序 | Reciprocal Rank Fusion | reranker/cross-encoder | 先低成本提升混合结果；重排属于可选高延迟步骤 |
| Agent 协议 | 内部最小工具 schema + MCP stdio | 通用 Flow 引擎 | 当前需要可审计的文件操作，不需要通用编排平台 |
| 任务执行 | 进程内持久任务表 + 有界队列 | Worker Thread / 独立进程 | 先降低复杂度；CPU 或稳定性基准达标后再隔离 |

### 6.2 不立即采用的方案

- 不把 LangChain、Dify Flow 或通用 Agent 框架作为核心依赖；会引入较大的抽象、升级和调试成本。
- 不立即上 pgvector、Qdrant、LanceDB；单机个人库尚未证明需要外部服务或原生扩展。
- 不立即做 CRDT、实时协作、插件市场和自建同步云；这些会改变产品边界，而不是解决当前用户路径问题。
- 不把自动摘要、自动标签、自动双链设计为不可撤销的写操作；所有模型建议先经过用户可见确认。

## 7. 接口与数据契约优化

### 7.1 API 演进原则

现有 `/api` 在 0.x 阶段保持兼容；新增能力先遵守当前错误结构和请求 ID，不为尚未稳定的个人桌面接口过早做微服务式版本爆炸。进入 1.0 后再提供 `/api/v1` 别名和弃用周期。

### 7.2 关键接口

| 接口 | 优化方向 |
| --- | --- |
| `POST /api/ai/chat/stream` | SSE 事件统一为 `meta`、`status`、`delta`、`citation`、`tool`、`done`、`error`；返回 `requestId`、`sessionId`、`usage` 和降级原因 |
| `POST /api/ai/index/reindex` | 返回 `202 { jobId }`；不阻塞请求；支持取消、重试、暂停和模型变更后的全量重建 |
| `GET /api/ai/index/status` | 返回 job 状态、总量、已处理、失败、排队、当前模型、最后错误和更新时间 |
| `POST /api/ai/retrieval/preview` | 返回 keyword、semantic、fusion 三路候选和最终上下文；默认脱敏，显式 debug 权限才返回完整 excerpt |
| `POST /api/ai/operations/preview` | 返回规范化动作、风险、冲突版本、planHash 和过期时间 |
| `POST /api/ai/operations/execute` | 强制校验 planHash、角色、Vault 路径、目标版本和幂等键；执行结果逐项返回 |
| `POST/PATCH /api/notes` | 增加 `Idempotency-Key` 和 `If-Match`；版本不匹配返回 409，前端进入合并/重载流程 |
| `GET /api/notes` | 保留 offset 兼容，同时新增 cursor；列表默认只返回 excerpt，不拉取完整正文 |
| `POST /api/attachments` | 使用 multipart 或受控 raw body，服务端生成存储名并返回 sha256、mime、size、引用状态 |
| `GET /api/jobs/:id` | 统一索引、摘要、导出、扫描和冲突任务的状态读取接口 |

### 7.3 数据表演进

现有 `notes`、`links`、`tags`、`notes_fts`、`note_chunks`、`note_chunk_embeddings`、`ai_index_state`、会话和审计表继续保留；新增或补强：

| 表/投影 | 用途 |
| --- | --- |
| `jobs` | `type/status/progress/attempts/error/idempotency_key/created_at/updated_at`，所有后台工作统一可恢复 |
| `retrieval_feedback` | query、命中块、用户相关/不相关反馈、算法版本；仅本地保存 |
| `retrieval_eval_cases` | 固定问题、期望 note/anchor、算法版本，用于离线回归 |
| `conflicts` | 外部同步冲突的两份路径、hash、时间、处理状态 |
| `attachments` | 路径、sha256、mime、size、mtime、引用计数 |
| `note_properties` 或 `notes.properties` | frontmatter 属性视图，必须可由 Markdown 重建 |

任何新增表都必须说明重建来源；如果不能从 Vault 重建，就不能成为事实真源。

## 8. 性能优化计划

### 8.1 服务端和数据层

1. watcher 事件按路径去重、延迟合并；避免每次保存触发多次投影和 AI 索引。
2. 基础投影和 Embedding 队列分离；Embedding 失败不能回滚用户刚保存的 Markdown。
3. 对 `title COLLATE NOCASE`、`file_path`、`content_hash`、链接目标标题建立索引；列表查询只取 excerpt。
4. 向量查询使用模型、维度和索引版本过滤；先扫描候选块，再按笔记聚合，避免一个笔记占满 top-k。
5. 线性扫描的升级门槛设为：基准库 50,000 个块、p95 查询超过 300ms 或事件循环阻塞超过 50ms，再评估 sqlite-vec/Worker Thread。
6. 外部 Provider 使用连接超时、AbortController、指数退避和有限重试；非幂等写请求默认不自动重试。

### 8.2 前端和桌面端

- Editor preview 对 Markdown 内容防抖 150–250ms，大文档按段落 hash 缓存解析结果。
- 所有 open/save/refresh 请求使用 AbortController 或递增序号，旧请求不能覆盖新笔记。
- 笔记列表使用分页或虚拟列表；初始加载不拉完整正文和全量索引。
- Canvas pointermove 用 `requestAnimationFrame` 合并，卡片 `memo`，节点查找使用 `Map`。
- AI SSE 支持取消、重连提示和中断后保留已经收到的文本；不能使用假打字动画掩盖上游延迟。
- Electron GPU/renderer 崩溃保留现有降级，但将启动失败、后端退出和日志路径显示给用户。

## 9. 用户体验设计

### 9.1 AI 面板

AI 面板保持三种明确状态：

1. **本地可用**：关键词检索、Markdown 检查、最近修改和文件列表，即使未配置模型也能使用。
2. **模型已连接**：显示当前 Provider、模型、是否发送笔记内容、流式响应和引用来源。
3. **降级/失败**：明确显示“模型失败/语义索引未就绪/已回退到关键词”，提供重试或打开设置，不静默伪装成功。

每条回答的引用都应支持：点击打开笔记、跳到标题锚点、查看命中摘要；没有引用的普通闲聊必须标明未使用知识库。

### 9.2 写操作

文件写入采用三段式体验：

```text
自然语言请求 → 动作预览/风险/冲突提示 → 用户确认 → 执行结果/审计/撤销入口
```

预览中显示实际路径、变更摘要、覆盖风险和是否会把内容发送给外部模型。用户不能只看到“已完成”而不知道改了哪些文件。

### 9.3 索引与任务

模型中心显示当前 Embedding 模型、隐私提示、已索引/待索引/失败数量和“重建索引”按钮。任务页显示开始时间、耗时、失败原因和重试；关闭应用后任务可在下次启动恢复或明确标记中断。

### 9.4 快捷路径

- `Ctrl/Cmd + K`：快速打开和搜索。
- `Ctrl/Cmd + D`：打开或创建每日笔记。
- 编辑器选中文本：改写、摘要、翻译、续写，结果先进入草稿。
- 关系面板：相关笔记、已存在链接、悬空链接和一键接受建议分组显示。

## 10. 分阶段实施计划与验收门禁

### 阶段 0：基线和硬化，1 周

**工作项**：纳入 Git、CI/发布门禁、写入一致性、Key 存储、Host/CSP/symlink、Agent 提示注入测试、统一任务表设计。

**退出条件**：

- `npm run verify`、构建、迁移空库和 MCP E2E 全部通过。
- 人工制造磁盘写失败、模型 401/429/超时、进程中断、重复请求和恶意路径，均无静默丢失或越权写入。
- 所有危险工具调用有 planHash、确认、审计和可定位 requestId。

### 阶段 1：索引与检索质量，2–3 周

**工作项**：后台任务、索引进度/恢复、模型指纹、混合检索评测集、引用事件、检索调试视图、反馈入口。

**退出条件**：

- 1,000、5,000、20,000 篇基准库的基础索引不阻塞 API；单文件保存不会触发全库 Embedding。
- 固定评测集 Recall@5 ≥ 0.80，引用有效率 100%；不满足时必须能看到失败的召回链路。
- 语义服务不可用时，关键词检索仍可用，UI 明确说明降级。

### 阶段 2：基本盘，3–5 周

**工作项**：附件、模板、每日笔记、大纲、版本历史、静态导出。

**退出条件**：

- 创建/编辑/移动/删除/恢复后，Markdown 真源、SQLite 投影和 UI 一致。
- 断电或杀进程后重启，未完成任务可恢复或标记，不出现半写文件。
- 任意历史版本可预览和恢复，恢复动作可再次撤销。

### 阶段 3：AI 原生工作流，2–3 周

**工作项**：相关笔记、自动双链建议、受控标签、每日摘要来源、选中文本写作助手、MCP 权限收口。

**退出条件**：

- 建议默认为只读；接受后使用当前版本写入，发生并发修改则要求重新确认。
- 自动双链建议的接受/忽略反馈可导出为本地评测数据。
- 摘要和 Agent 任务均可查看来源、运行记录、失败原因和取消状态。

### 阶段 4：规模化选项，按基准决定

**候选项**：Worker Thread、sqlite-vec、本地 Embedding、WebDAV/S3 + E2EE、PWA、可选的独立 collector。

**进入条件**：只有当数据规模、延迟、内存或用户需求超过当前架构阈值时进入；每项先增加可回滚的适配器和对照基准，不直接替换真源。

## 11. 效果评估标准

### 11.1 性能基准

测试库至少包含 1k/5k/20k 篇 Markdown、中文/英文混合、短文/长文和双链/标签/Canvas。每组重复 30 次，报告 p50/p95/p99、CPU、内存和事件循环阻塞。

| 指标 | 目标 |
| --- | --- |
| 冷启动到可编辑 | 5k 篇库 ≤ 3s；全量 repair 单独显示进度 |
| 打开已索引笔记 | p95 ≤ 150ms，不拉取无关全文 |
| 关键词搜索 | 5k 篇库 p95 ≤ 200ms |
| 混合语义搜索 | 20k 块库 p95 ≤ 500ms，不含无法控制的远程模型首包；分别记录 Embedding 和本地检索耗时 |
| 自动保存确认 | p95 ≤ 300ms；保存不等待 Embedding |
| 流式首 token | Provider 网络独立记录；Lattice 自身从请求到转发 ≤ 100ms |
| 失败索引恢复 | 重启后 100% 可识别待处理/失败任务，不丢失 Markdown |
| 前端长列表 | 5k 条目滚动无明显布局抖动，内存随可视区近似稳定 |

### 11.2 检索与模型质量

- Recall@5、MRR@5、nDCG@5：覆盖中文同义词、简称、标题锚点、跨笔记链接和无答案问题。
- 引用有效率：引用的 note id/path/anchor 必须来自服务端检索结果，目标 100%。
- 引用覆盖率：对需要知识库事实的问题，至少 90% 的参考回答带可点击来源。
- 无答案诚实率：评测集没有答案时，模型不能伪造本地来源；目标 100% 不出现虚构路径。
- 工具安全：危险写操作拦截率 100%；未确认写入数为 0；重复请求幂等。

### 11.3 数据可靠性与安全

- 1,000 次自动保存、外部修改、改名、删除和重启组合测试后，真源和投影可重新一致。
- 同步冲突保留两份内容，零静默覆盖；解决动作可审计。
- API Key 不出现在日志、普通前端状态、错误详情和导出配置明文中。
- 依赖、SAST、Electron URL/IPC、Markdown/SVG、Vault traversal、提示注入测试作为发布阻断项。

### 11.4 用户体验

- 5–8 名目标用户完成“创建笔记 → 搜索 → AI 问答 → 点击引用 → 接受双链 → 回滚版本”的任务成功率 ≥ 95%。
- 首次配置模型不超过 3 个关键步骤；未配置模型时，核心笔记功能不被遮挡。
- 任何长任务都有状态、进度、取消或失败原因；任何自动写入都有确认或明确的自动化授权。

## 12. ADR：关键架构决定

### ADR-001：继续使用文件真源 + SQLite 可重建投影

**状态**：Proposed  
**决策**：Markdown/Canvas/Vault 资产是真源；SQLite、向量和任务表均可删除重建。  
**理由**：符合本地优先、可迁移和第三方同步；避免块级数据库的备份与升级税。  
**代价**：需要 watcher、增量索引、冲突处理和文件原子写入。  
**替代方案**：SQLite/CRDT 为真源，拒绝，因与当前产品定位和可读文件承诺冲突。

### ADR-002：保留模块化单体，后台任务逐步隔离

**状态**：Proposed  
**决策**：继续 Express + Node `node:sqlite` 单进程；用持久任务表、有界队列和接口边界承载长任务，只有基准证明必要时再上 Worker Thread/独立 collector。  
**理由**：单机单用户目前不需要微服务运维；可先获得任务恢复、进度和性能收益。  
**代价**：需要防止同步 SQLite/文件 I/O 阻塞事件循环。  
**替代方案**：直接拆微服务，拒绝，因部署、升级、IPC 和本地数据一致性成本过高。

### ADR-003：混合检索优先，重排按评测启用

**状态**：Proposed  
**决策**：FTS5/trigram + Embedding + RRF 为默认链路；reranker、sqlite-vec 和本地模型均是可插拔后置选项。  
**理由**：中文子串检索、语义召回和零服务依赖互补；可以在不牺牲启动复杂度的前提下覆盖个人库规模。  
**代价**：需要评测集和分数解释，否则混合排序难以调优。  
**替代方案**：只用向量或直接引入向量数据库，分别会损失精确词面能力或增加部署成本。

### ADR-004：AI 写操作采用显式计划和确认

**状态**：Accepted by current implementation, needs hardening  
**决策**：模型只能生成动作计划；服务端做路径/角色/版本校验，用户确认后执行，全部动作审计。  
**理由**：文件系统写入不可逆风险高，笔记内容又可能包含提示注入。  
**代价**：比“一句话直接改完”多一次交互；可通过低风险读操作自动执行保持效率。

## 13. 风险与回滚

| 风险 | 触发信号 | 缓解/回滚 |
| --- | --- | --- |
| 远程 Embedding 泄露隐私或不稳定 | 用户关闭语义索引、429/超时上升 | 关闭 Embedding 即回退 FTS；UI 提前说明数据出站 |
| 模型更换导致维度/排序失效 | model/dim 不一致、Recall 下降 | 索引按模型指纹隔离，旧向量保留到新索引完成 |
| Agent 被笔记内容诱导 | 工具参数异常、越权路径、未确认写入 | 内容与系统指令分区、工具白名单、planHash、回归攻击集 |
| 线性向量扫描拖慢主线程 | p95 > 300ms、事件循环阻塞 | feature flag 关闭语义查询，评估 sqlite-vec/Worker Thread |
| 版本历史占用空间 | `.lattice/history` 持续增长 | 保留策略、空间提示、用户可清理，清理前生成备份 |
| 第三方同步产生覆盖 | conflicts 增长或重复文件增加 | 冲突面板保留两份，不做静默合并；先完成 C1 再做内置同步 |

## 14. 最终实施顺序

```text
版本控制/安全/写入一致性
          ↓
任务表 + 增量索引 + 评测集 + 可观测性
          ↓
附件 / 模板 / 每日笔记 / 大纲 / 历史 / 导出
          ↓
语义搜索 / 引用问答 / 相关笔记 / 自动双链
          ↓
MCP 权限完善 / 定时自动化 / 规模化适配器
```

最终目标不是让 Lattice 成为一个缩小版 Dify，而是让它成为“文件真源可靠、中文检索强、AI 引用可信、文件操作可控、离线仍可用”的本地知识工作台。只有当上述指标在固定数据集、真实模型和目标机器上持续通过，才可以对外宣称达到行业领先水平。
