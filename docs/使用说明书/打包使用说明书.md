# 格物 Lattice 打包使用说明书

**适用版本：0.1.1**
**目标平台：Windows x64**  
**文档用途：维护者构建 Windows 发行产物；普通用户不需要阅读或执行本手册。**

本项目目前保留两种 Windows 打包方法：

| 方法 | 入口 | 适用场景 | 默认输出 |
| --- | --- | --- | --- |
| 方法一：Electron Builder | desktop/ | 项目自带、最直接的桌面发行流程 | desktop/release/ |
| 方法二：winpack | 仓库外 tools/packer/ | 使用统一的运行壳、产物检查和多目标打包流程 | dist/winpack/ |

两种方法都使用 Electron，产物都包含前端、Express 后端和本地 SQLite 运行环境。它们是两条独立的打包链，不要把一套方法的输出目录、配置文件或命令混用。

---

## 一、打包前准备

### 1.1 环境要求

- Windows x64
- Node.js 22，建议使用不低于 22.9.0 的版本
- npm 可正常访问依赖源，或已经准备好本地 npm 缓存
- 仓库目录：D:\source\Item\init\FCNode\lattice
- winpack 工具目录：D:\source\Item\init\FCNode\tools\packer

检查 Node.js 和 npm：

~~~powershell
node --version
npm --version
~~~

### 1.2 安装依赖并构建前端

在仓库根目录执行：

~~~powershell
Set-Location D:\source\Item\init\FCNode\lattice

npm run setup
npm --prefix desktop install
npm run build
~~~

命令作用：

- npm run setup：安装 server/ 和 web/ 的依赖。
- npm --prefix desktop install：安装 Electron 及 Electron Builder。
- npm run build：生成 web/dist/，桌面包和 winpack 都依赖这个前端产物。

方法一的 pack、dist、dist:installer 和 dist:portable 会自动再次构建前端；方法二的 winpack build 使用已有的 web/dist/，所以修改前端后必须重新执行 npm run build。

### 1.3 发布前检查版本和资源

当前版本是 0.1.1。发布新版本时，至少检查并同步以下文件中的版本号：

~~~text
package.json
server/package.json
web/package.json
desktop/package.json
packaging/winpack/winpack.config.jsonc
~~~

同时确认以下资源存在：

~~~text
web/dist/index.html
desktop/build/icon.ico
desktop/assets/icon.ico
server/src/
packaging/winpack/entry.mjs
~~~

如果更换应用图标，桌面打包和 winpack 都使用 desktop/build/icon.ico 作为打包图标；运行时窗口图标还会使用 desktop/assets/icon.ico。

## 二、方法一：desktop Electron Builder

### 2.1 配置位置

- npm 脚本：desktop/package.json
- Electron Builder 配置：desktop/electron-builder.yml
- 输出目录：desktop/release/
- 应用可执行文件名：lattice.exe
- Windows 架构：x64
- Electron：由 desktop/package.json 中的依赖版本决定
- asar：关闭，后端的 ESM 加载和迁移文件需要普通文件布局

### 2.2 生成未安装目录

适合先在本机直接启动验证：

~~~powershell
Set-Location D:\source\Item\init\FCNode\lattice\desktop
npm run pack
~~~

输出：

~~~text
desktop/release/win-unpacked/lattice.exe
~~~

可以直接双击 lattice.exe 启动，也可以把整个 win-unpacked 文件夹交给测试人员验证。不要只复制其中一个 exe，Electron 运行所需的 DLL 和资源也必须保留。

### 2.3 同时生成安装版和绿色版

~~~powershell
Set-Location D:\source\Item\init\FCNode\lattice\desktop
npm run dist
~~~

主要输出：

~~~text
desktop/release/Lattice-0.1.1-setup.exe
desktop/release/Lattice-0.1.1-portable.exe
desktop/release/win-unpacked/lattice.exe
~~~

### 2.4 只生成安装版或绿色版

只生成安装版：

~~~powershell
Set-Location D:\source\Item\init\FCNode\lattice\desktop
npm run dist:installer
~~~

只生成绿色版：

~~~powershell
Set-Location D:\source\Item\init\FCNode\lattice\desktop
npm run dist:portable
~~~

安装版和绿色版的文件名分别是：

~~~text
Lattice-0.1.1-setup.exe
Lattice-0.1.1-portable.exe
~~~

### 2.5 方法一的运行数据

- 安装版默认将用户数据保存到 %APPDATA%\Lattice\。
- 绿色版优先将数据保存到 exe 同级的 LatticeData\，这样可以连同文件夹一起迁移。
- 首次运行时再选择或配置 Vault 文件夹；不要把 Vault 和程序安装目录混为一谈。
- 日志位于数据目录下的 logs\lattice.log。
- 卸载安装版时会保留用户数据，避免误删笔记。

绿色版应放在用户具有写入权限的目录，例如 D:\Tools\Lattice\。不建议直接放到 C:\Program Files\，否则无法写入同级数据目录时会失去便携效果。

## 三、方法二：winpack

### 3.1 配置和工具位置

- winpack 配置：packaging/winpack/winpack.config.jsonc
- winpack 入口：packaging/winpack/entry.mjs
- 外部打包工具：D:\source\Item\init\FCNode\tools\packer
- 输出目录：dist/winpack/
- 首选端口：5188；端口被占用时会自动选择可用端口
- 就绪检查：/ready
- Windows 架构：x64
- 打包目标：dir、portable、nsis

winpack 的 input 指向仓库根目录，但只会按照配置中的 files 白名单收集运行所需文件，并从 server/ 收集生产依赖。不要手动把整个 node_modules/、.git/ 或开发缓存复制到发布目录。

### 3.2 打包前构建

如果还没有安装依赖，在仓库根目录执行：

~~~powershell
Set-Location D:\source\Item\init\FCNode\lattice

npm run setup
npm --prefix desktop install
npm run build
~~~

desktop/node_modules 需要存在，因为 winpack 配置通过 runtime.builderModules 复用其中的 Electron Builder 模块。

### 3.3 查看配置解析结果

从 tools/packer 目录执行：

~~~powershell
$Repo = "D:\source\Item\init\FCNode\lattice"
$Packer = "D:\source\Item\init\FCNode\tools\packer"

Set-Location $Packer

node bin/winpack.mjs info --config "$Repo\packaging\winpack\winpack.config.jsonc"
~~~

重点确认输出中的以下内容：

- 输入目录是仓库根目录。
- 入口是 packaging/winpack/entry.mjs。
- 输出目录是 dist/winpack。
- 目标包含 win32/dir[x64]、win32/portable[x64] 和 win32/nsis[x64]。
- 依赖来源是 server/。

### 3.4 生成全部 winpack 产物

~~~powershell
$Repo = "D:\source\Item\init\FCNode\lattice"
$Packer = "D:\source\Item\init\FCNode\tools\packer"

Set-Location $Packer

node bin/winpack.mjs build --config "$Repo\packaging\winpack\winpack.config.jsonc"
~~~

主要输出：

~~~text
dist/winpack/lattice-0.1.1-x64-portable.exe
dist/winpack/lattice-0.1.1-x64-setup.exe
dist/winpack/win-unpacked/lattice.exe
dist/winpack/winpack-manifest.json
~~~

只生成单个目标时，可以使用命令行覆盖配置中的目标。例如只生成绿色版：

~~~powershell
node bin/winpack.mjs build --config "$Repo\packaging\winpack\winpack.config.jsonc" --target portable
~~~

### 3.5 验证 winpack 产物

建议至少验证解包目录：

~~~powershell
node bin/winpack.mjs verify "$Repo\dist\winpack\win-unpacked"
~~~

验证会检查：

- 产物是否存在以及目录是否完整。
- PE 头和 Windows x64 架构是否正确。
- 子系统是否为 Windows GUI。
- exe 是否嵌入图标。
- 产品名、文件版本和版权信息是否写入。

也可以一次验证多个目标：

~~~powershell
node bin/winpack.mjs verify "$Repo\dist\winpack\win-unpacked" "$Repo\dist\winpack\lattice-0.1.1-x64-portable.exe" "$Repo\dist\winpack\lattice-0.1.1-x64-setup.exe"
~~~

### 3.6 使用可视化界面

winpack 还提供可视化入口，适合查看配置和执行打包：

~~~powershell
$Repo = "D:\source\Item\init\FCNode\lattice"
Set-Location D:\source\Item\init\FCNode\tools\packer

node bin/winpack.mjs ui --cwd "$Repo\packaging\winpack"
~~~

可视化界面使用的仍是 winpack.config.jsonc，完成后仍应使用 verify 做命令行体检。

### 3.7 方法二的运行数据和日志

winpack 的应用名为 ASCII 名称 lattice，这个名称同时参与 exe 和数据目录定位：

- 绿色版优先使用 exe 同级的 lattice\ 数据目录。
- 安装版优先使用 exe 所在目录；目录不可写时回退到 Electron 的用户数据目录，通常位于 %APPDATA%。
- 运行时会将数据目录通过 WINPACK_DATA_DIR 传给 Lattice 后端。
- 日志位于数据目录下的 logs\main.log。
- main.log 超过 5 MB 时会轮转为 main.log.1。

winpack 运行壳还负责单实例、端口选择、/ready 就绪检查以及 GPU 崩溃后的自愈处理。应用关闭时不要强制结束进程，以免 SQLite 的 WAL 文件来不及整理。

## 四、两种方法的产物对照

| 用途 | 方法一：Electron Builder | 方法二：winpack |
| --- | --- | --- |
| 未安装目录 | desktop/release/win-unpacked/ | dist/winpack/win-unpacked/ |
| 安装版 | desktop/release/Lattice-0.1.1-setup.exe | dist/winpack/lattice-0.1.1-x64-setup.exe |
| 绿色版 | desktop/release/Lattice-0.1.1-portable.exe | dist/winpack/lattice-0.1.1-x64-portable.exe |
| 产物清单 | 无统一 manifest | dist/winpack/winpack-manifest.json |
| 配置文件 | desktop/electron-builder.yml | packaging/winpack/winpack.config.jsonc |
| 构建入口 | desktop/package.json | tools/packer/bin/winpack.mjs |

两个方案的 exe 文件名不同，这是预期行为。发布时请选择其中一套产物，不要将两套文件混在同一个发布压缩包内。

## 五、发布前验证清单

### 构建内容

- [ ] 已重新执行 npm run build，web/dist/index.html 存在。
- [ ] 已确认版本号在各 package 和打包配置中一致。
- [ ] 已确认 desktop/build/icon.ico 和运行时图标存在。
- [ ] 已确认没有把开发用 .env、数据库、日志或整个仓库目录放进产物。

### 功能启动

- [ ] 首次启动可以创建数据库并显示界面。
- [ ] 可以选择 Vault 并读取 Markdown 文件。
- [ ] 新建、编辑、保存笔记后重新启动，数据仍然存在。
- [ ] 白板、标签页、设置和背景图片功能可正常使用。
- [ ] 关闭程序后再次启动不会残留第二个实例。

### 产物检查

- [ ] 安装版可以安装、启动和卸载。
- [ ] 绿色版放入普通可写目录后可以启动，并能在同级创建数据目录。
- [ ] winpack 产物已执行 node bin/winpack.mjs verify ...。
- [ ] 发行前已在一台没有开发环境的 Windows x64 机器上测试。
- [ ] 已备份要发布的 exe、版本号和对应的校验信息。

## 六、常见问题

### 6.1 启动后白屏或提示前端文件不存在

重新生成前端：

~~~powershell
Set-Location D:\source\Item\init\FCNode\lattice
npm run build
~~~

然后重新执行对应打包命令。不要只替换 exe；前端文件是随包复制的运行资源。

### 6.2 winpack 提示找不到 Electron Builder 或依赖

确认以下步骤都执行过：

~~~powershell
Set-Location D:\source\Item\init\FCNode\lattice
npm run setup
npm --prefix desktop install
npm run build
~~~

再检查 desktop/node_modules 和 server/node_modules 是否存在。

### 6.3 绿色版没有把数据放在 exe 旁边

把整个绿色版放到普通可写目录，例如 D:\Tools\Lattice\，不要直接放在 C:\Program Files\。如果目录没有写入权限，运行壳会为了保证数据可写而回退到用户数据目录。

### 6.4 端口 5188 被占用

这是预期可恢复情况。packaging/winpack/entry.mjs 会先尝试 5188，被占用时自动选择系统分配的可用端口，窗口仍会正常打开。

### 6.5 产物验证失败

先确认验证的路径指向本次构建的产物，再重新构建。不要对安装程序的临时解压目录和旧版本目录混用验证。推荐使用：

~~~powershell
node bin/winpack.mjs verify "D:\source\Item\init\FCNode\lattice\dist\winpack\win-unpacked"
~~~

### 6.6 修改版本号后文件名没有变化

方法一读取 desktop/package.json 的版本，方法二读取 packaging/winpack/winpack.config.jsonc 的版本。修改后必须重新运行对应打包命令；旧的 release/ 或 dist/winpack/ 文件不会自动改名。

## 七、推荐发布流程

如果需要发布正式版本，推荐按以下顺序执行：

1. 更新并核对所有版本号和图标资源。
2. 执行测试和前端构建：npm run verify、npm run build。
3. 选择一种打包方法生成产物。
4. 启动 win-unpacked 做本机冒烟测试。
5. 对最终安装版和绿色版执行 winpack verify，或使用等效的人工检查。
6. 在无 Node.js、无项目源码的 Windows x64 机器上安装并运行。
7. 发布安装版、绿色版及版本说明；不要发布 win-unpacked 目录，除非它用于内部测试。

两种方法都可以生成可用发行版本。若需要统一的构建清单、目标覆盖和产物体检，使用方法二；若只需要快速生成本项目原生的桌面安装包，使用方法一。
