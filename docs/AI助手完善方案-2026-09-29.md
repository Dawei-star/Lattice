## 一、我们的现状（一句话版）

笔记基本盘扎实（双链/图谱/FTS5 中文检索/白板/增量投影同步），AI 助手已有「对话 + 文件操作代理 + 审计 + 模型管理中心」的骨架，但 AI 层存在六个硬伤：

| # | 硬伤 | 位置 |
|---|------|------|
| 1 | 无流式输出，长回复靠假打字动画干等 | `ai.service.js:445-454` |
| 2 | 无 RAG/向量检索/语义搜索，上下文靠「截断 12000 字符 + 前 100 条文件索引」 | `AIAssistantPanel.jsx:92-104` |
| 3 | `references` 由模型自由生成、服务端不校验，会编造笔记路径 | `ai.service.js:616-621` |
| 4 | API Key 明文存 localStorage，且每次请求明文 POST 给 server | `aiSettings.js:111`、`AIAssistantPanel.jsx:132-137` |
| 5 | 对话记忆是假长期记忆（localStorage 40 条，换端即失忆） | `AIAssistantPanel.jsx:13,80` |
| 6 | 模型失败静默回落本地规则助手，用户可能误把兜底当模型回答 | `ai.service.js:33-39` |

### 2.2 各项目要点与不足

**AnythingLLM（技术栈与我们几乎 1:1，首要参考）**
- 功能：全功能 RAG（带引用来源）、Agent Flows 无代码编排、MCP 兼容、Workspace 多用户、可嵌入挂件、音频转录/TTS、动态模型路由。
- 架构：Monorepo 三件套 —— Vite+React 前端 / Express server / **独立 collector 进程做文档解析**（重活隔离）；向量库默认嵌入式 LanceDB，零配置。
- 不足：RAG 是最大抱怨源——官方 FAQ 专设「为什么模型不用我的文档」；切块后只取 top 片段导致模型看不到全文（issue #2121）；r/LocalLLM 有「nightmare」热帖。根因都在**切块策略与上下文管理**，不是工具本身。

**Khoj（功能形态的靶子）**
- 功能：笔记/PDF/Notion 问答带可溯源引用、语义搜索、自定义 Agent、**定时自动化任务**（定期跑研究并推送结果）、图像生成、语音。
- 架构：Postgres + pgvector；本地模式用 GGUF 量化 MiniLM 交叉编码器；关键词搜索 + TF-IDF 打标签可完全离线。
- 不足：自托管必须 Postgres + Docker，对桌面软件太重；本地小模型质量与云差距明显。

**Reor（定位最像我们，但已死——最重要的一课）**
- 功能：笔记自动分块 embed；**写作时侧栏自动浮现相关笔记**；对笔记 RAG 问答。核心隐喻「一个有两个生成器的 RAG 应用：LLM 和人类」值得记住。
- 架构：Electron；Markdown 文件为真源（同我们）；Transformers.js 全本地 embedding；LanceDB 嵌入式向量库。
- 不足与死因：**2026-03 归档**。大库索引慢、模型下载体验差、纯本地小模型问答质量上限低。教训：全本地重 RAG 路线维护成本极高；「自动相关笔记推荐」这个功能形态本身已被验证是杀手级。

**Smart Connections（零配置语义搜索的标杆）**
- 内置本地小模型（bge-micro-v2 级），**无 API key、装上即用**，自动索引；Connections 视图（写这篇时全库相关笔记浮现）+ Lookup 语义搜索。
- 不足：大 vault 首次 embed 慢、CPU 占用高、重索引问题。

**FastGPT（知识库质量的做法）**
- QA 对切分（比纯段落切分更适合笔记语料）、chunk 人工编辑、**混合检索 + 重排**、单点检索测试调试、全调用链日志。
- 「FastGPT 知识库强，Dify 工具链强」是社区共识——我们要抄的是它的检索质量工程，不是 Dify 的管线规模。

**思源 / Logseq（对我们底座的印证）**
- 思源：块级双链 + SQLite 索引 + 内置 `siyuan` CLI（全文/语义/SQL 查询）+ AGENTS.md，把自己定位成 Agent 可操作的知识库。
- Logseq：稳定版停滞、押注 SQLite DB 版重写三年仍是 beta。**我们「文件真源 + SQLite 投影」的架构天然站在 Logseq 重写想到达的位置上，这是做 AI 的巨大优势**（SQL 直查 + 引用稳定 ID + FTS5 现成）。

**Open WebUI / LobeChat（对话侧标配）**
- 标配 = 多模型切换、SSE 流式、多会话管理、MCP 工具、引用展示。UI 细节值得逐屏研究。

### 2.3 行业共识（做完这些才算及格）

1. **OpenAI 兼容层 + 本地/云双轨**：无一例外；「自定义 base URL」是最低要求（我们已有）。
2. **带引用来源的 RAG 问答**：回答必须可点回原文，否则文档问答不被信任。
3. **语义搜索/相关笔记推荐**：比聊天更高频、更刚需（Reor/Smart Connections 验证）。
4. **SSE 流式 + 多会话**：没有就是不及格。
5. **MCP**：2025 年后新功能出现频率最高的关键词（思源、AFFiNE、AnythingLLM、LobeChat 全接入）。
6. **Agent/工具调用**：第二梯队标配；定时自动化是差异化亮点（Khoj）。

### 2.4 前人踩过的坑

- **「模型不用我的文档」**：RAG 最高频抱怨。解法 = 可调切块策略 + 检索调试视图 + 引用展示，三者缺一不可。
- **索引性能**：必须增量索引（只 embed 变更块）、后台低优先级队列、进度可见、可暂停。
- **隐私边界要显式**：Copilot Plus 闭源后端、AFFiNE 许可争议、AnythingLLM 默认遥测都反噬过口碑。「数据何时离开本机」必须可见、可关——这正是我们「本地优先」卖点的一部分。
- **纯本地小模型质量天花板**：Reor 之死的深层原因。务实解是**两层设计**：本地 embedding 保隐私 + LLM 云/本地可选，并诚实告知取舍。
- **先做薄、快交付**：Logseq 重写三年、AFFiNE 信任危机的教训——AI 功能先交付「好用的语义搜索 + 带引用的问答」，Agent/自动化后置。

## 三、改进方案（四阶段路线图）

原则：顺着 `docs/同类项目对标与增强方案-2026-09-28.md` 的 D 主线，按「先修硬伤 → 补标配 → 建护城河」排序；不破坏「零原生依赖、文件为真源」两条底线。

### 阶段 0：修硬伤（1 周内，均为小改动）

| 项 | 做法 |
|---|---|
| **SSE 流式输出** | 请求体加 `stream:true`，上游 SSE 转发到客户端。我们已有 SSE 基建（`/api/vault/events`），照搬即可。前端去掉假打字动画，改为真流式 + 停止按钮 |
| **引用来源服务端校验** | `references` 返回前逐条比对 notes 表（标题/路径存在性），失效引用剔除或标记「未验证」，杜绝编造路径（`ai.service.js:616-621` 一带） |
| **失败透明化** | 取消静默回落：模型失败时明确展示「模型调用失败 + 原因 + 重试按钮」，本地兜底回答必须带显著「本地规则」徽标 |
| **Key 安全** | 桌面端用 Electron `safeStorage` 加密存储 key，server 端启动时注入；Web 端至少不再随每次请求回传明文 key（server 持有即可） |
| **会话持久化** | 新增 `ai_sessions` / `ai_messages` 表（SQLite），对话历史入服务端，跨端可用；localStorage 仅作缓存 |

### 阶段 1：语义搜索 + 本地索引（2-3 周，核心价值）

对应 D1，形态抄 Smart Connections + Reor：

1. **Embedding 双轨**
   - 云轨：OpenAI 兼容 `/v1/embeddings`（硅基流动 bge-m3、智谱 embedding-3 等都在现有 18 家预设内，加一个 embedding 模型配置项即可）。
   - 本地轨（可选，后置）：Transformers.js + bge-micro 级小模型，纯 JS 不破坏零原生依赖。
   - UI 上明示「云端 embedding 意味着笔记分块会发往该服务商」——隐私边界显式化。
2. **存储**：`note_chunks`（note_id, chunk_path 标题锚点, content, hash, model, dim）+ `note_chunk_embeddings`（chunk_id, vector BLOB）。向量用 Float32Array 序列化 BLOB 存 node:sqlite，**JS 暴力余弦**——个人库规模（数千笔记 × 数十分块 ≈ 10⁴-10⁵ 向量）单次查询 <10ms，完全够用；不引入 sqlite-vec/LanceDB 等原生依赖。超过 5 万分块再考虑迁移。
3. **增量索引管道**：复用现有 watcher → `applyVaultChange` 链路，content_hash 变化才重新分块/embed；后台队列低优先级 + 进度条 + 暂停/恢复（这是 Smart Connections 被骂最多的点，必须一开始就做对）。
4. **切块策略**：按标题层级切（我们已有 `[[标题#小节]]` 锚点体系），块 500-800 字、重叠 10%；保留笔记级 frontmatter 元数据。
5. **新功能出口**：
   - 「相关笔记」侧栏（编辑时自动浮现，Reor 验证过的杀手级形态）；
   - 全局语义搜索并入现有搜索（FTS5 关键词 + 向量语义双路，RRF 融合排序——Open WebUI 模式）。

### 阶段 2：带引用的知识库问答（2 周，AI 助手升级）

对应 D3，抄 FastGPT 的质量工程 + AnythingLLM 的教训：

1. **混合召回**：query → FTS5 bm25 + 向量余弦双路 → RRF 融合 → top-k（默认 6，可调）分块进上下文；替换现在「前 100 条文件索引」的浪费式注入。
2. **上下文组装用足我们的独有优势**：命中分块后，**沿双链/嵌入引用扩展一跳**相关笔记摘要；标题锚点让引用可精确到小节。这是纯文档 RAG 产品做不到、我们双链底座独有的能力。
3. **引用强制落地**：prompt 要求模型输出引用 `[n]` 标号 → 服务端将标号映射为真实 chunk → 前端渲染可点击引用卡，点击跳转对应笔记小节。
4. **检索调试视图**（抄 FastGPT）：设置里给一个「检索测试」面板，输入 query 展示双路命中 chunk、分数、最终入选——RAG 调优挫败感的最大解药。
5. **「读全文」逃生门**：命中分块所属笔记若不大（<8k 字），自动整文注入（解决 AnythingLLM「模型看不到全文」的经典抱怨）。

### 阶段 3：AI 原生化写作辅助（2-3 周）

对应 D2/D4 + Khoj/Copilot 的形态：

1. **自动双链建议**：保存笔记后后台跑「当前笔记 × 全库语义相似」+ 实体匹配，侧栏给出建议链接（接受/忽略），接受即写回 `[[ ]]`。这是双链软件 AI 化的差异化主打。
2. **写作助手**：编辑器内选中文本菜单（续写/改写/摘要/翻译），流式插入；模板化 prompt（抄 Text Generator 形态）。
3. **自动打标**：基于既有标签词表做受控打标建议（不做自由生成，冷启动用现有标签云）。
4. **每日智能摘要**：Khoj Automations 的简化版——定期（如每日）汇总「今日修改笔记 + 建议关注」，生成为一篇真实笔记。

### 阶段 4：生态位（按需）

1. **会话/工具体系**：AI 对话升级为带工具循环的真 Agent（read/search/semantic_search/create/update 已是现成工具集），沿用现有 preview→confirm→execute 安全边界。
2. **MCP Server 暴露**：把笔记库做成 MCP server（search_notes / read_note / create_note 等工具），让 Claude 等外部 Agent 能读写 vault——抄思源的定位，成本最低、生态收益最大的方向。
3. **定时自动化**：Khoj 形态的定期研究任务（依赖阶段 3.4 的基建）。

### 明确不做（延续既有共识）

实时协作 CRDT、插件市场、块级模型、自建同步云、可视化工作流编排（Dify 形态）、全本地 LLM 强绑定。

## 四、优先级一句话总结

**先做阶段 0 的流式 + 引用校验 + 失败透明化（体验及格线）→ 立刻上阶段 1 语义搜索/相关笔记（比聊天更刚需、双链软件的差异化）→ 阶段 2 带引用问答（信任分水岭）→ 阶段 3/4 逐步建护城河。**

整个方案不引入任何原生依赖，全部复用「文件真源 + SQLite 投影 + SSE + OpenAI 兼容层」的既有底座；最大的架构优势（双链图 + 标题锚点 + SQLite）恰好是纯文档 RAG 竞品没有的，上下文组装和引用粒度可以做出别人做不到的深度。
