# 批量任务拆解

任务模式的价值在于「一次说清，多轮做完」，但**批量指令天然有边界模糊的风险**：
「整理一下全库」既可以指 12 篇，也可以指 4000 篇，差别在于你要不要先说清楚。

**本Skill 只读**：不生成任何写入动作，只负责把任务切清楚。写入由后续回合的写操作完成。

## 先确定范围，再谈计划

在拆批之前必须先回答三个问题，答不上来就不要往下写计划：

1. **命中范围**：这次任务覆盖哪些笔记？用 search 给出实际数量，不要用「大概」「应该」。
   如果用户说的是「全库」，先跑一次全库统计并把数字报出来——用户很可能不知道自己的库有多大。
2. **判定依据**：每一批是按什么规则选出来的？（路径前缀 / 标签 / 标题模式 / 修改时间 / 无入链）
   规则必须是**可复述、可复核**的，例如「`Work/` 下且带 `#2024` 标签」，而不是「相关的笔记」。
3. **不做什么**：明确排除什么。`_templates`、`.lattice`、附件目录、画布文件一律不动；
   用户没提到的目录不因为「顺带」而纳入。

## 分批原则

- **单轮动作上限 30 个、单轮自动读取上限 5 个**——这是系统硬限制，批次设计必须落在限额内，
  否则最后一批会被静默丢弃，只能靠用户发「继续」补跑。
- **按依赖顺序排批**：先建目录 / 先补链接，再移动文件。反过来的批次会因为目标不存在而整批失败。
- **每批只做一类动作**。把重命名、移动、改写内容混在一批里，失败时无法判断是哪一步的问题，
  只能整批重来。
- **批次大小递减**：第一批取最有代表性的少量样本（3–5 个）。等用户在确认清单里核对过、
  确认判定规则没问题，再推进后续批次。**不要一次抛出两百个动作让用户逐条核对**——
  超过二十条 humans 就不再看了，这等于没有确认。

## 输出格式

- `batches`：批次列表。每批写清动作类型、目标清单、**这一批做完后的验收方式**
  （例如「移动后确认原路径已无文件、目标路径已存在」）。
- `excluded`：明确排除的条目与理由，逐条列出，不要合并成一句话。
- `verification`：整体任务的完成判据。必须可被用户独立复核，例如「全库搜索 `旧前缀` 应返回 0 条」。

不确定某篇笔记该不该纳入时，放进 `excluded` 并说明原因，**不要塞进批次赌一把**。
宁可少做一批，也不要让用户在几十条动作里挑出你判断错的那一条。
