# Lattice AI 权限说明书

> 日期：2026-10-26 · 分支：`phase/p1-rust-ai` · 状态：现行实现说明（非提案）
> 配套图：`permission-flow.html`（同目录，可播放的判定链路）
> 关联：`doc/AI/地基/Lattice-AI地基架构方案.md` §5.5、§11 安全基线；`doc/AI/地基/ai-interaction-flow.html`（请求链路）

**一句话：** 权限不是一道"拦不拦"的开关，而是三道互不替代的闸——**AI 有没有手（能力）→ 这一下有多危险（分级）→ 要不要先问人（策略）**。三者的判定依据、代码落点、可配置性都不同，混在一处就会长出"看起来能配、实际没用"的假控件。

---

## 1. 设计立场

| # | 立场 | 理由 | 体现 |
|---|---|---|---|
| P1 | 档位管"问不问"，不能覆盖拒绝 | 一旦任何档位能撤销 deny 规则，安全层就只剩一句免责声明 | L3 不受任何档位影响（`runner.rs` 的 L2 免确认条件写死 `level == L2`） |
| P2 | 更严者胜 | 用户放宽、专家收紧时，结果必须是收紧 | 专家 `disabled` 压过用户 `skip`；用户 `always` 压过专家 `auto` |
| P3 | 可撤销优先于可拦截 | 拦不住的意图，至少要能回滚 | 写前快照 + `operationId`，`FileChangesCard` 提供撤销 |
| P4 | 默认保守且诚实 | 默认值决定绝大多数人的实际风险敞口 | 默认 `approvalPolicy = 'review'`；标签按真实状态显示，不用"为我审核"掩盖"其实不能写" |
| P5 | 档位不改别的设置 | 选审批策略顺手改模型偏好，是权限系统最典型的越权 | 菜单只写 `approvalPolicy`（+ 写入必需的 `interactionMode`） |

## 2. 三层模型

| 层 | 回答的问题 | 事实源 | 代码位置 |
|---|---|---|---|
| **能力层** | AI 有没有"手" | `interactionMode`（只对话 / 任务）+ provider 的 `nativeTools` 实测 | `AIAssistantPanel.tsx` 工具面注入；`buildAiAgentBudget` |
| **分级层** | 这一次写操作有多危险 | 动作类型 × 外部性 × 批量规模 | `web/src/lib/ai-policy.ts` ↔ `src-tauri/src/ai/core/agent/risk.rs` |
| **策略层** | 要不要先给用户看 | `approvalPolicy`（档位）+ `allowIrreversible`（豁免）+ 专家 `writePolicy` | `src-tauri/src/ai/core/agent/runner.rs` 的 gate 判定 |

三层是**串联**的：能力层不过，后面两层不参与（AI 连"想写"都表达不出来）；分级层给出等级，策略层据此决定放行还是挂起。

策略层内部再分两个**正交**维度：档位管"日常打扰程度"（问得多不多），豁免管"要不要放弃最后一道防线"（L3 还拦不拦）。把两者塞进同一个控件，就会出现"名字承诺全跳、实际还拦一半"的名实不符——这正是本方案把豁免拆成独立开关的原因。

### 2.1 为什么分级层要双实现

前端 `classifyAiWriteRisk` 与后端 `classify_write_risk` 各有一份实现：前端要在构建预览时立刻告诉用户"这是 L2"，后端要在执行前独立复核。两侧行为由 `src-tauri/tests/fixtures/risk-classification.json` 同断言钉死，任何一侧改判定都必须同时改夹具。

这不是冗余，是**不信任前端**：请求经过 IPC 边界后，前端的"我已经判过了"不构成依据。

## 3. 主体与范围

### 3.1 角色

| 角色 | 读 | 写 | 说明 |
|---|---|---|---|
| `viewer` | 允许 | **拒绝** | 前端的工具网关与后端 runner 双侧拒绝，不依赖单侧 |
| `editor` | 允许 | 允许（受分级与策略约束） | 本地桌面端固定使用此角色（`LOCAL_OWNER_ROLE = 'editor'`） |

本地 Lattice 没有远程 ACL 服务，`actor` 恒为 `local-user`。角色存在是为了让"以后加多用户"不必重写判定链——判定接口已经在了，只缺一个下发角色的服务。

### 3.2 路径范围

AI 能碰的路径不是"整个知识库"，而是**当前上下文范围解析出的文件集合**：

```
allowedPaths = scopedNoteIndex.map(note => note.filePath).filter(Boolean).sort()
permissionVersion = "local-paths-" + 指纹(allowedPaths)
```

- 任何工具调用的路径参数（`path` / `targetPath` / `sourcePath` / `fromPath` / `toPath`）都必须落在某个 `allowedPaths` 前缀之内。
- 绝对路径、含 `..` 的路径、空路径一律视为非法。
- `permissionVersion` 参与检索缓存键：范围变了，缓存自然失效，不会拿旧范围的检索结果去回答新范围的问题。

### 3.3 专家收紧

专家可声明 `scopeExclude`（前缀黑名单）与 `writePolicy`：

| writePolicy | 写工具是否出现在工具面 | L2 是否免确认 |
|---|---|---|
| `disabled` | 否（剥离） | — |
| `confirm` | 是 | 否 |
| `auto` | 是 | 是（L3 仍不免） |

`scopeExclude` 在 runner 里对 `path` 与 `targetPath` 同时检查——移动/复制的落点也算写入。

### 3.4 默认拒绝（fail closed）

以下情况在**执行前**就结束，且不会因为任何审批档位而放行：

| 条件 | 拒绝原因 |
|---|---|
| 工具未注册 | `未注册的工具` |
| 必填参数缺失/类型不符 | `缺少必填参数：…` |
| 角色为 `viewer` 且是写工具 | `viewer 角色不能执行写工具` |
| 路径越界或非法 | `超出授权路径范围：…` |
| 专家 `writePolicy = disabled` | `当前角色禁止写入` |
| 命中专家 `scopeExclude` | `超出专家允许的写入范围` |
| 工具预算耗尽 | `工具调用预算已耗尽` |
| 不可信内容驱动 L2/L3 写 | `不可信内容不能直接驱动高风险写操作` |
| 预览后计划被改动（`planHash` 不符） | 拒绝执行 |

## 4. 风险分级 L0–L3

判定顺序**不可交换**——先看是不是写、再看会不会出去、最后才看是不是自己的草稿：

```text
type ∉ 已知写类型                      → L0  只读或非写操作
external ∨ type ∈ {删除/外发/权限} ∨ batchSize > 1 → L3
type = create ∧ (AI 自有草稿 ∨ 目标不存在)        → L1
其余                                   → L2
```

| 等级 | 含义 | 可逆 | 需要确认 |
|---|---|---|---|
| **L0** | 只读或未识别的非写动作 | 是 | 否 |
| **L1** | 新建或修改 AI 自己的草稿 | 是（快照） | 否（「始终询问」档除外） |
| **L2** | 修改用户已有内容 | 是（快照） | 是 |
| **L3** | 删除 / 外发 / 发布 / 分享 / 改权限 / 批量 > 1 / 影响外部系统 | 语义上不可逆；**技术上删除与批量仍可快照撤销** | 是，默认免不开 |

已知写类型：`create` `write` `update` `edit` `move` `copy` `archive` `delete` `remove` `purge` `send` `publish` `share` `permission` `permissions`。
破坏性类型：`delete` `remove` `purge` `send` `publish` `share` `permission` `permissions`。

**三点容易忽略的后果：**

1. `batchSize > 1` 直接进 L3。所以"把 10 篇笔记整理成周报"必然走确认，不管用户选了什么档位。这是有意的：批量写的影响面不随单篇风险线性增长。
2. `targetExists !== true` 即视为新建（L1）。路径不存在时宁可当"新建"，也不当"覆盖"——但如果模型给了一个拼错的目标路径，用户看到的是 L1 而非 L2，预览卡片仍需扫一眼路径。
3. **分级表比工具面宽**。分级表为未来的外发/分享/改权限预留了入口，但当前 AI 写工具只支持 `create` / `update` / `delete` / `move` / `copy` 五种（`tools.rs` 的 `WRITE_ACTION_TYPES`）。所以 L3 在今天实际只由**删除**与**批量**触发，"外发"类路径尚未接入——等 MCP / 联网能力上线，那条闸才真正承重。

## 5. 审批策略（四档）

| 档位 | 内部值 | 能力 | L1 | L2 | L3 |
|---|---|---|---|---|---|
| **只对话** | `interactionMode = 'quick'` | 只读 | — | — | — |
| **始终询问** | `approvalPolicy = 'always'` | 可写 | 预览确认 | 预览确认 | 预览确认 |
| **为我审核**（默认） | `approvalPolicy = 'review'` | 可写 | 直接执行 | 预览确认 | 预览确认 |
| **自动执行** | `approvalPolicy = 'skip'` | 可写 | 直接执行 | 直接执行 | **预览确认** |

> **命名说明**：这一档原名"跳过所有审批"，但 L3 恒定要确认，字面承诺兑现不了，属于名实不符，已改为「自动执行」。名字描述行为，不承诺"绝不多问"。真正想要零确认的用户走 §5.4 的独立高危豁免开关，而不是靠档位名字暗示。

### 5.1 每档的真实落点

| 判定 | 位置 | 逻辑 |
|---|---|---|
| 是否注入写工具 | 前端 | `只对话` 时不注入 `lattice_file_operation` |
| L1 是否自动执行 | 前端 | `approvalPolicy !== 'always'` 才允许走自动执行分支 |
| L2 是否免确认 | 后端 | `approvalPolicy === 'skip'` → `auto_approve_l2 = true` |
| 是否连 L1 都挂起 | 后端 | `approvalPolicy === 'always'` → `confirm_all_writes = true` |
| L3 是否挂起 | 后端 | **与档位无关**，`NeedsConfirmation` 恒定 |

前端那行判断不是重复劳动：后端把 L1 挂起后，前端若仍按"L1 可自动执行"处理，就会绕过内核的挂起直接调执行接口。两处必须同时拦。

### 5.2 gate 判定的优先级

```text
用户已确认该调用            → Granted（只出现在确认续跑轮）
confirm_all_writes          → NeedsConfirmation（「始终询问」）
requires_confirmation ∧ ¬(auto_approve_l2 ∧ L2) → NeedsConfirmation
其余                        → Auto
```

顺序即优先级：已确认 > 用户要求全问 > 策略免确认 > 自动。专家 `auto` 与用户 `always` 同时存在时，`confirm_all_writes` 在第二个分支先命中，所以**更严者胜**。

### 5.3 为什么"自动执行"档还留着 L3

四家主流实现的取舍（2026-10 官方文档/源码）：

| 产品 | 档位 | 最宽松档是否仍有硬闸 |
|---|---|---|
| Claude Code | default / acceptEdits / plan / auto / dontAsk / bypassPermissions | 有。「任何模式都不自动批准」清单含识别到的 `rm`/`rmdir` 关键路径删除、显式 ask 规则、需交互工具；`disableBypassPermissionsMode` 可锁死 |
| Cursor | Auto-review / Allowlist / Run Everything | 有。File-Deletion / External-File / Browser Protection 叠在模式之上，模式再宽松也会要求批准 |
| Gemini CLI | plan < default < autoEdit < yolo | 有。policy engine 的 deny/ask 与审批模式**正交**，管理员策略压过个人 |
| Cline | 分项 Auto Approve / YOLO | 无。YOLO 明确"关闭所有安全检查"且无二次确认 |

三家保留、一家全放。差别不在于"信任用户与否"，而在于**不可逆的外发动作不该由一条设置项顺手打开**——Lattice 的快照救得回"改错了"，救不回"发出去了"。

需要说明的是：**这条理由在今天还没有完全兑现**。当前 AI 写工具面不含外发/分享/改权限，L3 实际拦的是删除与批量，而删除本身有快照可撤销。所以 L3 目前的真实作用是"高影响面的动作先看一眼"，而不是"防止不可逆损失"——后者要等外发类能力接入才成立。

### 5.4 高危豁免：把"要不要放弃最后一道防线"拆出来

档位答不了"我就是要全自动"这个需求，硬堵在门外不合理；把 L3 豁免塞进档位又会让名字骗人。解法是再加一个**与档位正交**的独立开关：

| 项 | 值 | 说明 |
|---|---|---|
| 字段 | `allowIrreversible`（布尔） | 与 `approvalPolicy` 平行，不参与档位派生 |
| 默认 | `false` | 不主动放弃任何防线 |
| 生效条件 | 仅「自动执行」档 | 其他档位本来就要问，开关不改变行为 |
| 开启方式 | 菜单内独立勾选行 + **二次确认弹窗** | 弹窗写明"删除与批量写入有快照但不会自动提示找回" |
| 后端落点 | `RunnerInput.allow_irreversible` → 仅放开 L3 | L1/L2 的免确认仍由 `auto_approve_l2` 决定 |
| 优先级 | 低于 `confirm_all_writes` | 「始终询问」压过豁免：说了每次都要问，就是每次都要问 |

开启后的实际行为：L0–L3 全部自动执行，AI 不再弹出任何确认卡片。

界面上它被放在菜单最底部、用分隔线隔开、默认勾选框为空、说明文字写"仅在「自动执行」档下可用"——视觉上要像"另开一把锁"，而不是第五个档位。开启时弹一次后果说明，用户点"我已了解，开启"才生效；关闭则不需要确认。

这一层是**正交豁免**而非**权限提升**：它只影响 L3 的"问不问"，不影响角色、路径范围、专家 `writePolicy`、预算与幂等。

## 6. 执行链路

对应 `permission-flow.html` 的六段：

| 段 | 发生了什么 | 关键点 |
|---|---|---|
| ① 能力边界 | 用户下指令 → 前端按档位决定工具面 → 工具网关 preflight | 没有工具就没有写动作；越权在这里就被挡 |
| ② 提出与预检 | 模型返回 `toolCalls` → 内核接管写轮 | 模型只表达意图，不执行 |
| ③ 风险定级 | 内核逐调用 `classify_write_risk` | 与前端同断言 |
| ④ 确认闸门 | gate 判定 → 挂起 / 放行；挂起时前端出预览，用户确认后带 `planHash` 继续 | 计划被改过就拒绝 |
| ⑤ 落盘 | 串行执行 → 写前快照 → 返回 `operationId` | 读并行、写串行 |
| ⑥ 兜底 | L3 恒定挂起 · 预算截断 · 幂等去重 · 快照撤销 | 不看档位 |

挂起期间：**请求正文只在进程内存**，落盘的是经 `redact_request_secrets` 白名单裁剪的元数据（`runId` / `message` / `mode` / `approvalPolicy` / `actor` / `role` / `expertId` 等），密钥与文件内容不落盘。

## 7. 确认、撤销与恢复

### 7.1 一次确认的完整生命周期

```text
预览请求 → 服务端生成 plan + planHash
        → 前端渲染变更项（类型 / 路径 / 完整路径 / 变更摘要 / 可撤销性）
        → 用户点确认 → 携带 planHash 提交
        → 服务端校验 planHash → 执行 → 返回 operationId
```

`planHash` 是防"预览时看的是 A，执行的是 B"的唯一手段。前端不允许在确认后改写动作内容。

### 7.2 二次确认

删除走两道：前端 `useFileConfirmation` 的阻断式卡片（"继续删除"→"确认删除"），以及后端 `has_delete` 标记触发的额外确认要求。前端卡片只针对删除，其他写操作保持即时反馈——因为手动操作的发起人就是用户自己，不需要再问一次。

### 7.3 断点续跑

Run 中断后恢复时，挂起写批次（`PendingWriteConfirmation`）随恢复记录一起还原，已完成的步骤按 `checkpoint` 跳过，不会重复写。已执行部分用 `operationId` 对齐，避免"恢复了但写了两遍"。

### 7.4 撤销

每次写前生成快照，`operationId` 是撤销的句柄。`AiFileChangesCard` 展示本轮变更并暴露撤销入口；文件内核的删除同样可撤销（`file_undo` 还原，`file_delete_requires_second_confirmation_and_undo_restores` 钉死了这条链路）。

但要注意 `reversible` 字段的口径差异：它表达的是**语义上的不可逆**（东西没了、外发出去了），不是"技术上无法撤销"。删除动作 `reversible = false` 却仍能被 `file_undo` 还原；批量写 `reversible = true` 但一次影响面很大。界面文案要按各自的口径写，不能拿一个字段覆盖两种含义。

## 8. 预算、幂等与重试

| 项 | quick（只对话） | task（三档写入） |
|---|---|---|
| 最大步数 | 4 | 12 |
| 最大工具调用 | 6 | 24 |
| 最大 token | 6,000 | 16,000 |
| 最大时长 | 30s | 120s |

- 预算耗尽后不再执行任何调用，返回 `预算已耗尽`，不会"最后一个也放过去"。
- 幂等键：`runId:callId:toolName`。同一 run 内重复的幂等调用直接返回缓存结果。
- 重试：仅幂等工具重试，上限 3 次，指数退避；`AbortError` 不重试。

## 9. 配置与迁移

| 项 | 位置 | 说明 |
|---|---|---|
| 审批策略 | `localStorage["lattice-ai-settings-v1"]` 的 `approvalPolicy` | 按终端计，不同步到服务端 |
| 高危豁免 | 同上，`allowIrreversible` | 默认 `false`；开启需在界面上二次确认 |
| 交互模式 | 同上，`interactionMode` | `quick` / `task` |
| 旧字段 | `autoApprove`（已移除） | `true → skip`，其余 `→ review` |
| 请求透传 | `approvalPolicy`（camelCase） | 内核读取后转换为 gate 布尔 |

迁移规则刻意**不放大权限**：旧版 `autoApprove: true` 的用户升级后仍是「自动执行」，其余人一律落到"为我审核"，不会因为字段改名而突然获得全自动。同时 `interactionMode` 不再由旧布尔推导——否则升级用户点"只对话"会被旧值拉回任务模式。

## 10. 已知边界

1. **模型不支持工具调用时，三档写入全部不可用**（`nativeTools === false`）。菜单会禁用并给出原因，而不是让用户选了之后静默失败。
2. **浏览器开发模式不经过内核**：直连 HTTP 服务，没有挂起写批次，也没有断点续跑。权限判定仍在，但恢复语义弱于桌面端。
3. **专家 `disabled` 的手伸不到工具面**：工具被剥离后，模型不会"先提议再被拒"，因为看不到工具。这是有意的——降低无效轮次，也避免模型在说明里描述一个它其实做不了的动作。
4. **没有"单次会话提权"**：想全自动只能改全局设置（档位或 §5.4 的豁免开关），改完就会一直生效。下一步该补的是"仅本次会话/仅本目录"的临时提权。
5. **`reversible` 字段有口径歧义**：删除标 `false`（语义不可逆）但技术上 `file_undo` 能还原；批量写标 `true`（可撤销）但影响面大。别拿这个字段直接渲染"可撤销 / 不可撤销"两个标签，也别按等级推断。
6. **并发 run 未做跨 run 的写冲突检测**：两个 run 同时改同一文件，后写覆盖先写，靠快照撤销而非锁。
