# Kimi Code AI 工具完整流程（借鉴参考 v1）

> 来源：Kimi Code Desktop（本机实际运行的 AI 编码代理）行为拆解
> 日期：2026-10-26 · 用途：为 Lattice 的 AI 内核（ai-core）设计提供参照
> 说明：本文描述的是"运行中的 Kimi Code 代理"的真实工作机制，不是产品宣传文档。所有机制均可在同目录其他方案中对照 Lattice 的分层落地。

---

## 0. 一句话概括

**模型负责"想"（推理与决策），工具负责"做"（文件、命令、网络），两者通过一个带终止条件的循环反复配合，直到任务完成。** 代理本身不理解文件系统之外的东西——它"看到"的世界只有用户消息和工具返回的文本结果。

---

## 1. 运行架构总览

### 1.1 分层

| 层 | 角色 | 说明 |
|---|---|---|
| 宿主应用 | Kimi Code Desktop | 提供聊天界面、会话持久化、权限弹窗、后台任务面板 |
| 代理循环（agent loop） | 会话进程内 | 管理消息序列、发起模型调用、执行工具调用、处理中断与压缩 |
| 模型服务 | Moonshot AI 服务端 | 只负责"给定输入 → 输出文本/工具调用"，无副作用 |
| 本地执行面 | 用户机器 | Bash 直接执行；文件读写走工作目录；浏览器走内置协议；子代理走独立循环实例 |

### 1.2 关键约束

- **非沙箱**：Bash 命令直接作用于用户系统，改动即时生效。代理靠"权限确认 + 风险判断"而非隔离来保证安全。
- **工作目录锚定**：所有相对路径解析到 `/home/bot/项目/other/item/init/lattice/Lattice`，访问外部路径必须用绝对路径。
- **无隐藏状态**：磁盘上的文件是事实来源。模型记忆里的"当前文件内容"可能过期，因此任何精确改动前必须先 Read。

## 2. 核心循环（Agent Loop）——逐步拆解

这是整个系统最重要的一段，完整展开如下：

```
┌─────────────────────────────────────────────────────────────┐
│ 1. 接收输入                                                  │
│   用户消息 / 系统提醒 / cron 触发 / 后台任务完成通知          │
├─────────────────────────────────────────────────────────────┤
│ 2. 组装上下文（prompt assembly）                             │
│   系统提示 + 工具清单 + 工作目录信息 + AGENTS.md             │
│   + 技能清单 + 历史消息 + 本轮工具结果                        │
├─────────────────────────────────────────────────────────────┤
│ 3. 模型推理                                                   │
│   输出：纯文本回复 / 工具调用请求 / 两者混合                  │
├─────────────────────────────────────────────────────────────┤
│ 4. 判定是否终止                                               │
│   无工具调用 → 结束本轮，输出最终回复                         │
│   有工具调用 → 继续                                           │
├─────────────────────────────────────────────────────────────┤
│ 5. 执行工具调用                                               │
│   可并行的多个调用放同一批；有依赖的串行                       │
│   危险操作触发权限确认                                        │
├─────────────────────────────────────────────────────────────┤
│ 6. 结果回注                                                   │
│   工具结果以结构化文本追加为新消息                            │
│   结果过长时截断并告知完整日志路径                            │
├─────────────────────────────────────────────────────────────┤
│ 7. 回到 2（循环）                                            │
└─────────────────────────────────────────────────────────────┘
```

### 2.1 每一步的细节

**第 2 步：上下文组装。** 系统提示是固定的骨架（身份、环境、工具使用规范、编码规范、风险动作原则、交付标准、上下文管理、技能说明）。每次调用前动态拼入：当前工作目录与目录树、项目级 `AGENTS.md`（作为参考数据而非特权指令）、可用技能清单、历史对话、以及上一轮全部工具的输出。

**第 3 步：模型输出的两种形态。**
- 纯文本 → 用户可见的回复
- 工具调用请求 → 形如 `{tool: "Read", args: {path: "..."}}` 的结构化块

模型可以在同一次输出里同时给文本和多个工具调用。

**第 5 步：并行与串行。** 互不依赖的调用必须放在同一批并行发起（这是系统提示里的硬性要求）；有依赖的必须串行。这个约束直接影响效率：一个"读 10 个文件"的任务是 1 轮而不是 10 轮。

**第 6 步：结果处理。** 工具输出有长度上限，超限会被截断并附带完整输出的保存路径（如后台任务的 `output_path`）。代理必须自己决定是读完整日志还是基于截断结果继续——这个"诚实汇报不完整信息"的行为是设计出来的：系统提示明确要求"基于部分结果不要假装完整"。

### 2.2 终止条件

循环结束于以下任一情况：
1. 模型不再请求工具调用 → 输出最终文本回复
2. 用户中断（`<system-reminder>` 提示 turn 被中断）→ 立即停止，部分输出作废
3. 后台任务失败/超时且无法继续 → 如实汇报而非编造结果
4. 达到轮次/token 上限 → 停止并说明未完成部分

## 3. 系统提示词骨架（代理的"宪法"）

系统提示不是装饰，它是行为的主要约束来源。Kimi Code 的系统提示包含以下章节，每一章都对应一类具体的行为规则：

| 章节 | 作用 | 关键约束 |
|---|---|---|
| 身份与目标 | 明确是编码代理 | 帮助用户完成软件工程任务 |
| 沟通规范 | 渲染、语言、路径引用 | Markdown 渲染；匹配用户语言；路径带行号可点击；外部路径用绝对路径 |
| 工具使用 | 优先级与并行规则 | 有专用工具就别用裸 shell；`cat`/`sed`/`grep` 等一律走专用工具；独立调用必须并行 |
| 编码规范 | 代码风格与测试 | 贴合周边代码；不假设库存在（先查 manifest）；不加无谓注释；项目无测试时不自造测试文件 |
| 风险动作 | 可逆性权衡 | 本地可逆操作自由做；难撤销/外溢操作必须先确认；被拒绝的调用不能换路重试 |
| 交付标准 | "完成"的定义 | 必须用项目自身的构建与测试命令验证；端到端跑通真实场景；测试红着不能宣布完成 |
| 上下文管理 | 压缩后的行为 | 压缩摘要视为准确记录，不重复已完成工作；但临时状态（文件、任务状态）必须用工具重新确认，不能信摘要里的旧值 |
| 技能机制 | 何时必须调用 Skill | 技能匹配请求时**强制**调用 Skill 工具，不得自由发挥 |
| 子代理规则 | 何时可派发 | 用户未要求时不派发；swarm/tower 模式或用户点名某类型代理才算授权 |

**这条对借鉴最重要：** "完成"是被严格定义的——不是"代码写完了"，而是"构建+测试命令在交付物上通过 + 用户原始场景端到端跑通"。

## 4. 工具体系

### 4.1 分类与设计意图

| 类别 | 工具 | 设计意图 |
|---|---|---|
| 文件读取 | `Read` | 带行号、支持大文件分页（`line_offset`/`n_lines`/`max_chars`）、识别编码（UTF-16 自动检测、GBK/二进制拒绝）、敏感文件（`.env`、私钥）拒绝读取 |
| 文件写入 | `Write` | 只用于新文件/整篇替换；增量修改**强制**用 `Edit` |
| 精确修改 | `Edit` | 精确字符串替换；强制先 Read 再 Edit；禁止连续两次 Edit 同一文件（防止 old_string 失效） |
| 搜索定位 | `Glob` / `Grep` | 替代 `find`/`rg`；尊重 `.gitignore`；默认跳过 `node_modules`/构建产物；敏感文件恒被过滤 |
| 命令执行 | `Bash` | 支持 `cwd`、超时、后台运行；foreground 默认 60s/上限 300s，超时自动转后台 |
| 网络检索 | `WebSearch` / `FetchURL` | 搜索给摘要+URL+日期，需全文时再 Fetch；只支持公网 http/https，无登录态 |
| 浏览器 | `mcp__desktop_browser__run` | 内置浏览器协议 `kimi.browser/1.0.0`；可导航/截图/元素交互/对话框应答；需控制标签页 |
| 任务编排 | `TodoList` / `TaskList` / `TaskOutput` / `WaitFor` | 进度面板；后台任务快照读取（非阻塞）；等待有明确规则（不能空等自己刚启动的任务） |
| 调度 | `CronCreate` / `CronDelete` / `CronList` | 会话内定时任务；recurring 7 天自动过期；火种带 jitter 防羊群效应 |
| 自主目标 | `CreateGoal` / `GetGoal` / `SetGoalBudget` / `UpdateGoal` | 目标模式：明确完成标准才可创建；连续 3 轮同一阻塞才可标 blocked |
| 技能 | `Skill` | 阻塞要求：技能匹配时**必须**调用 |
| 子代理 | `Agent` / `AgentSwarm` | 见 §5 |
| 计划模式 | `EnterPlanMode` / `ExitPlanMode` | 只读探索 → 写计划文件 → 请求批准 → 才可改代码 |

### 4.2 工具调用的几个硬规则

1. **专用工具优先于裸 shell。** `cat`/`head`/`tail` → Read；`sed`/`awk` 就地编辑 → Edit；`echo >` → Write；`grep`/`rg` → Grep；`find` 递归定位 → Glob。理由是专用工具走工作区访问策略、输出有上限、渲染更安全。
2. **`Read` 是 `Edit` 的前提。** 系统提示明文禁止"凭记忆或猜测的 old_string 调 Edit"。这是防止模型幻觉改动文件的主要护栏。
3. **`Bash` 不享受专用工具的守卫。** Grep/Read 会跳过 `.env` 和 `.git`，但 Bash 不拦——所以系统提示专门警告"绝不用 shell 读取/复制/传输秘密文件"。**这是工具设计上的安全缺口，靠行为规范补。**
4. **权限拒绝不可绕过。** 被拒绝的调用要调整方案或询问，绝不能换工具/换 shell 绕路重试。
5. **后台任务的诚实性。** 后台任务完成通知是"合成用户消息"到达，代理不能预测或编造其结果；未收到结果前不得声称完成。

## 5. 子代理（Subagent）机制

### 5.1 类型与能力

| 类型 | 工具集 | 用途 |
|---|---|---|
| `coder` | 全套（含编辑） | 通用软件工程，唯一能改代码的类型 |
| `explore` | 只读（Bash/Read/Glob/Grep/Web） | 快速代码库探索，可指定 thoroughness |
| `plan` | 只读 + Web | 只读规划与架构设计 |

### 5.2 生命周期与协作规则

- **冷启动**：子代理从零上下文开始，不继承父代理的对话。父代理必须在 prompt 里把所需信息全部写明（目标、已知事实、具体路径/命令）。
- **结果可见性**：子代理结果只对父代理可见，**不直接对用户可见**。父代理要负责把关键内容转述给用户。
- **不重复劳动**：子代理启动后，父代理不得并行重做其搜索/读取，也不得中途接手手工完成——这会抵消委派省下的上下文。
- **前台 vs 后台**：需要其结果才能继续 → 前台；有其他工作可并行 → 后台。禁止"后台启动后立刻空等"。
- **resume**：已完成工作优先 resume 而非新起一个，保留其上下文。
- **swarm 模式**：仅用户开启时可用 `AgentSwarm`；模板含 `{{item}}` 占位符；强制 ≥2 个 items 且展开后 prompt 必须互异；单次调用上限 128 个子代理。
- **授权门槛**：用户明确要求 / AGENTS.md 或技能指示 / 用户开启多代理模式，三者之一才算授权。"任务大""要深度研究"都不是授权理由。**这是防止代理过度委派、失控烧钱的关键闸门。**

## 6. 技能（Skills）机制

### 6.1 三级作用域与优先级

```
Project（项目级） > User（用户级） > Extra（插件级） > Built-in（内置）
```

同名字技能按此优先级取用。作用域标注让"用户说的'本项目的技能'指哪个"没有歧义。

### 6.2 运行期动态变更

技能目录在会话运行中会变化（插件安装、目录更新）。变化时系统提示被替换为最新清单，并附"DISREGARD any earlier skill listings"。**这要求代理始终以最新清单为准，不依赖渲染时的历史清单。**

### 6.3 强制调用规则

- 技能匹配请求时**必须**调用 `Skill` 工具，不得用自由文本回复替代。
- 技能目录更新后若该技能已加载过且 args 相同 → 直接遵循其指令，不重复调用；若 args 不同 → 重新调用。

### 6.4 技能内容形态

技能可以是目录（含 `SKILL.md`）或独立 `.md`，内容包含指令、示例、参考材料。插件型技能（如 `vercel-plugin`、`cloudbase`）会注入领域知识包，把"训练权重里过时的平台知识"刷新为当前事实——这是**对抗模型知识过期**的机制。

## 7. 权限与安全模型

### 7.1 权限模式

- `auto`：自动批准；`yolo`/`manual`：需批准
- `EnterPlanMode` 在各模式下都自动进入计划模式，但在 yolo/manual 下 `ExitPlanMode` 仍需用户批准

### 7.2 安全分层（重要：不是全有全无）

| 机制 | 覆盖 | 缺口 |
|---|---|---|
| 专用工具路径策略 | Grep/Read/Glob 尊重 workspace 访问策略，过滤 `.git`、`.env`、私钥 | — |
| Bash | **无**上述过滤 | 模型必须自律：绝不用 shell 读秘密文件 |
| 敏感文件拒绝 | Read 拒绝 `.env`、凭据库、SSH 私钥 | `.env.example`/公开密钥豁免，可正常读 |
| 写入前置检查 | Write 覆盖已存在文件前强制 Read | — |

### 7.3 风险动作分级

- **自由做**：本地、可逆的操作
- **必须先确认**：难撤销、外溢到本地环境之外的操作
- **被拒后**：调整方案或询问，禁止绕路
- **禁止**：非必要时求 root；git 变更类（commit/push/reset/rebase）仅用户要求时执行

## 8. 上下文管理与记忆

### 8.1 压缩（compaction）

- 临近上下文上限时自动压缩旧对话
- 压缩后保留：用户消息原文（尽量多）+ 一段第一人称工作摘要
- **摘要保留结论，不保留活状态**：文件、任务状态、后台作业等瞬时状态必须用工具重新确认

### 8.2 跨会话持久化

| 载体 | 生命周期 |
|---|---|
| 会话 wire 日志（`wire.jsonl`） | 会话内 |
| cron 任务 | 同一会话 resume 后恢复；**不跨新会话** |
| 目标（goal） | 活跃目标跨轮持续 |

### 8.3 上下文预算的隐性成本

子代理的意义不仅是并行，更是**上下文预算管理**：把探索性工作丢给子代理，父代理只接收结论。同理，技能按需加载而非全量注入。

## 9. 会话内的异步机制

### 9.1 后台任务

- `Bash(run_in_background=true)` / 后台子代理 / 后台提问
- 完成通知以合成消息在后续轮次到达
- 代理规则：不预测、不编造结果；未收到结果不得声称完成

### 9.2 等待语义（`WaitFor`）

- 仅当"确实没有其他工作可做 + 下一步依赖该结果"时才调用
- 等待期间不发 LLM 请求，但用户也在等
- 超时不是错误，返回仍在运行的任务列表
- 被等待的任务完成后只通知一次

### 9.3 cron

- 标准 5 字段 cron，用户本地时区
- 会话空闲时投递；活跃轮次中的触发被挂起到下一个空闲时刻
- 漏掉的多次触发合并为一次（`coalescedCount`），语义为"只看最新状态"
- 防羊群 jitter：周期 ≤10% 或 15 分钟的平移；`:00`/`:30` 的一次性任务最多提前 90 秒
- recurring 7 天后最后一次投递并自动删除（`stale: true` 标志）
- 活跃会话上限 50 个

### 9.4 对话框与用户接管

浏览器操作中若用户接管（`BROWSER_USER_TAKEOVER`），代理必须停止本轮浏览器调用，控制权在新的用户轮次恢复。

## 10. 浏览器工具的完整交互流程

这是内置浏览器协议 `kimi.browser/1.0.0` 的一次典型调用序列：

1. `browser.get_state` 发现现有标签页 / `browser.create_tab` 开新标签
2. `tab.navigate` / `tab.search` 到目标页
3. `page.elements.snapshot` 获取可交互元素的 ref 列表（TOON 表格形式）
4. `page.element.click` / `fill` / `type_text` 执行操作
5. `page.text.snapshot` 读取渲染后的 DOM 文本（有字符上限，用 cursor 翻页）
6. `page.visual.snapshot` + `page.visual.click` 处理视觉/坐标交互
7. `page.wait_for` 等待条件（元素可见/文本出现/URL 匹配）
8. `page.dialog.respond` 应答页面弹窗（alert/confirm/prompt/file）
9. `tab.wait_for_load` 等待 committed/dom_ready/complete
10. 结束：`browser.close_tab` / `browser.release_tab`

**控制规则：** 导航/输入/设备变更需要"控制"标签页；纯读页面不需要。控件在轮次结束时过期。每个结果都携带 `pendingDialogs`——任何弹窗在被应答前会持续出现在后续每次调用的结果里，代理必须优先处理弹窗再继续。

**与本项目的关系：** 用户明确要求用自己的 Chrome/Edge 或登录态会话时，改用 `kimi-webbridge` 技能而非内置浏览器。

## 11. 完整流程时序（一次典型编码任务）

以"在 Lattice 里给 ai-core 加一个 provider"为例，代理实际走过的路径：

| 轮次 | 代理动作 | 工具 | 说明 |
|---|---|---|---|
| 1 | 理解请求，判断是多文件非平凡改动 | — | 触发 EnterPlanMode |
| 2 | 只读探索相关代码 | Read/Glob/Grep（并行） | 计划模式下禁止改文件 |
| 3 | 写计划到计划文件，请求批准 | ExitPlanMode | 计划含具体文件/命令 |
| 4 | 批准后建立 todo 清单 | TodoList | 进度面板与实现同步 |
| 5 | 按 TDD 写测试 | Write | 项目有测试时才写 |
| 6 | 实现代码 | Edit（逐个文件，每改必先 Read） | 贴合周边风格 |
| 7 | 跑项目验证命令 | Bash | `npm run verify` 等项目自身命令 |
| 8 | 若测试红 → 修到绿；绿 → 收尾 | Edit/Bash | 红着不能宣布完成 |
| 9 | 清理 todo，汇报 | TodoList + 文本 | 汇报含验证证据 |

**注意第 7 步：** 用的是项目自己的验证命令，不是代理自创的。这是"交付标准"章节的落地。

## 13. 边界与不可靠之处（如实记录）

1. **模型版本不可自报。** 代理不知道当前会话的模型版本号/参数规模，只能查配置文件（`update-config` 技能读 `config.toml`）。
2. **无视觉感知。** 代理"看"到的是文本；截图需要浏览器工具配合，且截图本身代理无法读取（工具说明明文"你无法读取它"）。
3. **无登录态网络。** FetchURL 不带凭据，私有仓库/内部面板返回登录页而非内容——此时必须走有凭据的 CLI 或 MCP。
4. **Bash 无文件守卫。** §7.2 已述，这是设计上的真实缺口。
5. **压缩可能丢细节。** 摘要保留结论丢状态，代理必须在压缩后用工具重新确认瞬时状态——这个规则写进系统提示是有意为之，因为实践中出错率高。
6. **子代理结果不直达用户。** 父代理转述是信息唯一出口。
7. **计划模式的批准是用户的，不是代理的。** 代理不能自我批准。

## 14. 对 Lattice ai-core 的借鉴映射

| Kimi Code 机制 | Lattice ai-core 对应层 | 借鉴要点 |
|---|---|---|
| 代理循环（§2） | `ai/core/runtime` | 循环终止条件、结果回注、截断策略需显式设计；后台任务完成通知应建模为"合成事件"而非普通用户消息 |
| 系统提示骨架（§3） | `ai/core/prompt` | 系统提示是行为约束主体，必须有版本与覆盖机制（Lattice 现状：散落字符串，无版本） |
| 工具优先级规则（§4.2） | IPC 契约 + web 侧纯函数 | "专用工具优先于裸 shell"等规则本质是工具接口设计学：优先结构化接口，退化路径才用裸命令 |
| 子代理（§5） | 尚无 | 若引入需建模：冷启动上下文、结果回传路径、上下文预算控制；授权门槛必须显式（不可隐式开启） |
| 技能（§6） | 尚无 | 作用域优先级 + 目录动态刷新 + 强制调用三要素；对抗模型知识过期靠插件注入而非重训 |
| 权限分层（§7） | L0–L3 安全链 | Kimi 的缺口（Bash 无守卫）说明：安全必须落在**执行面**（工具实现），不能只靠行为规范 |
| 上下文压缩（§8） | `ai/core/context` | "摘要保结论不保状态"应写进压缩规范；压缩后状态重建是显式步骤 |
| cron/后台任务（§9） | durable run | 合并语义（coalescedCount）与 7 天过期值得直接借鉴；会话边界（不跨新会话）需在 Lattice 侧明确 |
| 交付标准（§3） | 验证门禁 | "构建+测试在交付物上通过 + 端到端场景跑通"应成为 ai-core 的完成判定，而非"代码写完" |
